## 1. 背景与目标

本仓库（`alanthinker/ninfer-4090-yarn`）是 RTX 4090（sm_89）上的 NInfer 引擎，含 YaRN 长上下文扩展。其预填充路径只实现了 FP8 计划（`AllowA8`），而 Ada 消费级卡没有 FP8 张量核；目标模型 `qwen3.8-27b`（`groupwise-int`，权重 Q4G64/Q5G64/W8G32）恰好是 INT8 张量核路径的目标格式。

因此本轮工作把另一条 4090 分支（Tensorninja/UDP，`ninfer-4090`）的优化移植进本基底：

- **P0a — SM 数自适应**：把散落在 5 个文件里的「170 SM（RTX 5090）」字面量换成运行时 `device_sm_count()`。
- **P2 — INT8 张量核预填充**：6 条 A8 路线（`linear_swiglu` q4 / `linear_add` q5 / `attn_input_proj` q4_q5 / `gdn_input_proj` q4_q5），含公共基础设施与 policy 下推。
- **P3 — CLI 兼容层**：接受 Tensorninja 拼写的参数，保证既有启动脚本不失效。

目标：在不改动用户生产服务（`qwen38`）的前提下，产出可直接替换的镜像，并给出端到端证据。

## 3. 测试环境与服务配置

服务端配置（merged 与 baseline 使用**完全相同**的参数）：

```
ninfer-serve /models/qwen3_8_27b_orcarouter.ninfer --model-id orcarouter
  --host 0.0.0.0 --port 8080
  --max-context 262144 --kv-capacity 262144 --kv-dtype rk4v4-e8
  --max-concurrency 4 --max-pending-requests 16 --pending-timeout-ms 600000
  --prefill-chunk 1024 --spec mtp --draft-tokens 3 --lm-head-draft
  --preserve-thinking --vision --vision-max-tokens 32768
```

- 容器：`--gpus all`，宿主机模型目录只读挂载，测试各用独立端口（merged 18080 / baseline 18081 / CLI 兼容 18082）。
- 冷启动：weights 16.9 GiB / 3m13s，engine ready 共 3m25s（两镜像一致）。
- 前置：先停用户生产容器 `qwen38`（占 ~30 GB）；测试完毕由 `/tmp/restore_qwen38.sh` 恢复。

### 度量口径（关键）

**不使用 curl 的 `time_starttransfer` 作为 TTFT**：流式响应会先收到 SSE 前导/keep-alive，`time_starttransfer` 会在预填充完成前就返回，数值无意义（实测同一个 70K 提示词得到 0.119 s 的假 TTFT）。

本报告统一采用**服务端 `timings` 块**（`ninfer-serve` 在响应与最后一个流式分块携带），即部署文档所要求的「服务端口径才是权威」：

| 字段 | 含义 |
|---|---|
| `prompt_n` / `prompt_per_second` | **已计算**的预填充 token 数与速率（前缀缓存命中不计入） |
| `predicted_n` / `predicted_per_second` | 解码 token 数与速率 |
| `draft_n` / `draft_n_accepted` | MTP 草稿数与接受数 |
| `cache_n` | 前缀缓存复用 token 数 |
| `ttft_ms` | 服务端口径首 token 延迟 |

## 6. 关键发现与偏差说明

### 6.1 「GDN 长输出崩溃」未能复现 → P0a 需重新归类

移植前的工作假设是：基底把网格尺寸按 RTX 5090 的 **170 SM** 硬编码，在 128 SM 的 4090 D 上会导致 cooperative launch 失败（`cudaErrorCooperativeLaunchTooLarge`），并在 GDN 长输出时崩溃。

**实测：基线镜像在同样的 GDN 长输出用例下完整完成了 13,474 token 的生成，日志中 0 条 CUDA 错误。**

复核 P0a 的 4 处改动，全部是**启动几何/调优阈值**而非正确性逻辑：

| 文件 | 原值 | 改动 | 性质 |
|---|---|---|---|
| `launcher/rmsnorm.cu` | 预取门控阈值 `170` 块 | `device_sm_count()` | 调优阈值 |
| `launcher/rope.cu` | 大 block 波容量 `1020 = 6×170` | `6 × device_sm_count()` | 调优阈值 |
| `gated_delta_net/chunked/output.cu` | 目标 CTA 数 `680 = 4×170` | `4 × device_sm_count()` | 调优阈值 |
| `sparse_moe/prefill_kernels.cu` | 持久块数 `510 = 3×170` | `3 × device_sm_count()` | 调优阈值（`__launch_bounds__(..,3)`） |

因此：

- 「崩溃」是**由源码审视推得的假设，不是观测到的事实**，本测试未能证伪基线可用性；
- P0a 的正确定位是**可移植性/调优修正**：在 128 SM 上错误几何会造成欠/过订阅与拖尾波（`sparse_moe` 的 510 块在 128 SM 上是 1.33 波，第二波仅 1/3 填充），**可能**是预填充增益的一部分来源，但在本报告中无法与 INT8 路线分离；
- 建议：**保留 P0a**（方向正确、零风险、且消除对具体零件的依赖），但文档与提交信息中**不要**声称它修复了一个已被观测的崩溃。

### 6.2 测试脚本自身的缺陷（已修正）

原 `/tmp/verify_merged.sh` 的 b) 用例生成 **1150 块**提示词（约 635K 字符 ≈ 400K token），**超过 262,144 上限**，服务会以 `context_length_exceeded` 直接拒绝：

```json
{"error":{"code":"context_length_exceeded",
          "message":"prepared prompt exceeds Engine max_context 262144"}}
```

本报告改用 **200 块**（110,619 字符 ≈ 70,221 token）的修正版，并在两镜像上以**同一脚本**运行以保证对照有效。

**衍生提示**：中文重复文本在此分词器下约 **1.57 字符/token**，按「字符数≈token 数」估算会高估约 57%。选提示词长度必须按 token 计。

## 8. 已知限制

1. MTP 接受率随内容可预测性波动（长文 42.1% / 代码 82.6%），因此**跨内容类型比较 tok/s 会失真**；本报告的 A/B 均在同内容、同参数下对比。
2. 增益拆分未做（INT8 路线 vs P0a 网格）——需要额外构建一个「仅 P0a」的中间镜像。
3. 未做 INT8 KV 与 E8 4-bit KV 的完整精度对照（本轮 CLI 用例中 int8 模式仅做启动与冒烟）。
4. 未复跑引擎自带的 CTest/ops 套件（本轮以端到端黑盒为验收口径）。
