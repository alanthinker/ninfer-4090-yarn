# NInfer 多分支源码深度分析与融合方案报告

**版本**：v2（依据端到端实测结论修订）
**范围**：RTX 4090 D（sm_89）上 NInfer 引擎的多分支能力盘点、取用决策与融合落地
**基底**：`alanthinker/ninfer-4090-yarn`（`origin/main` = `d26c7e50`，2026-09-21）
**目标模型**：`qwen3.8-27b` / `groupwise-int`（Q4G64 + Q5G64 + W8G32），原生 262,144 上下文
**实测依据**：见 [端到端部署与测试报告](端到端部署与测试报告.md)（merged vs baseline A/B）

> **本版改动摘要（相对 v1 方案）**
> 1. P2（INT8 预填充）**升格为已验证主项**：A/B 实测预填充 **+42.6% ~ +54.2%**。
> 2. P0a 由「崩溃修复」**降格重分类为「调优可移植性」**：端到端测试**未能复现**所谓 GDN 崩溃；上游该提交自身的措辞也是 straggler wave / 利用率，而非 cooperative launch 失败。
> 3. **新增发现（P0a 覆盖缺口）**：上游 `45a5ae57` 触及 10 个文件，我们只取了 6 个；**GQA attention decode 的波尺寸修正未移植**，而该处上游实测 **解码 −38.8%**（6.5–7k 上下文 / 6 query token）。
> 4. P5a（T=1 双缓冲 Ada MMA）**仍搁置**，依赖上游 272 行 `q4_small_t_mma.cuh` 分叉。
> 5. L3 磁盘层**放弃实现**，改由 `--slot-save-path` + `--auto-save-evicted` 覆盖。

## 3. 融合方案：取用矩阵

### 3.1 P2 — INT8 张量核预填充（**核心收益项**）

**来源**：TN。**做法**：整文件复制 + 最小化 wrapper 合并，保留上游作者与出处。

**新增 11 个文件**（其中 9 个与 TN **逐字节相同**，provenance 无损）：

| 文件 | 与 TN 的差异 |
|---|---|
| `src/ops/common/act_quant_g64.{cu,h}` | 完全相同 |
| `src/ops/common/int8_mma.cuh` | 完全相同 |
| `src/ops/common/int8_proj_launch.{cu,h}` | 完全相同 |
| `src/ops/common/int8_rowsplit_gemm.cuh` | 完全相同 |
| `src/ops/linear_swiglu/q4/q4_linear_swiglu_int8.cu` | 完全相同 |
| `src/ops/linear_swiglu/q4/q4_linear_swiglu_int8_gemm.cuh` | 完全相同 |
| `src/ops/linear_add/q5/q5_linear_add_int8.cu` | 完全相同 |
| `src/ops/attn_input_proj/q4_q5/q4_q5_attn_input_int8.cu` | 完全相同 |
| `src/ops/gdn_input_proj/q4_q5/q4_q5_gdn_input_int8.cu` | 完全相同 |

**修改 20 个既有文件**（policy 下推 + wrapper 合并 + 构建注册）：

| 分组 | 文件 |
|---|---|
| 公共头 | `include/ninfer/ops/attn_input_proj.h`、`include/ninfer/ops/gdn_input_proj.h` |
| 构建 | `src/CMakeLists.txt`（插入 6 条显式源文件条目；基底是显式列表，非 glob） |
| 公共 kernel 依赖 | `src/ops/common/mma.cuh`（补 `mma_s8_zero`） |
| op 家族 plan/kernels | `attn_input_proj/q4_q5/*_{kernels.h,plan.cpp,plan.h}`、`gdn_input_proj/q4_q5/*`、`linear_add/q5/*`、`linear_swiglu/q4/*` |
| wrapper（手工合并点） | `wrapper/attn_input_proj.cpp`、`wrapper/gdn_input_proj.cpp`、`wrapper/linear_add.cpp`、`wrapper/linear_swiglu.cpp` |
| 目标接线 | `src/targets/qwen3_6_27b/impl/variant.cpp` |

**设计对齐论证**（为什么可以整体复制）：基底在定稿前已把 policy 流进 FP8 op，只是**遗漏了 Q4/Q5 路线**；TN 把 policy 下推到 Q4/Q5 op 的方式与基底既有惯例一致，因此不是引入新范式，而是补齐同范式下的遗漏分支。

**接口差异与适配**：
- `linear_add` q5：基底 wrapper 多一个 FP8 分支 → 手工合并 2 处 Q5 门控。
- `attn_input_proj`：基底公共 API 是 `QType` 版本，policy 重载已存在 → 公共头只需补 `split + policy` 重载声明；wrapper 改 `split API → dispatch_split_parent` 并补 capacity 的 Q4/Q5 分支（**基底原本忽略 policy**，这是必须显式修的一处）。
- `gdn_input_proj`：plan/kernels 纯增量，形状与基底一致（5120/4096/12288/10240/6144）。
- `variant.cpp`：新增 3 个 policy 函数（V1）、7 处调用点（V2–V7，含给匿名 `phase` 参数命名）、5 处 capacity 函数。

### 3.2 P0a — SM 数自适应（**已部分融合，存在缺口**）

**来源**：UDP `45a5ae57`。上游该提交触及 **10 个文件**；我们取了 6 个：

| 上游文件 | 是否移植 | 上游实测收益 |
|---|---|---|
| `src/core/device.{cu,h}` | ✅ 已移植 | 基础设施（`device_sm_count()`） |
| `src/ops/launcher/rope.cu` | ✅ 已移植 | rope −5…9%（769–1020 token 带） |
| `src/ops/linear_attention/gated_delta_net/chunked/output.cu` | ✅ 已移植 | **中性**（上游明示「verified, not assumed」） |
| `src/ops/sparse_moe/decode/sparse_moe_decode_kernels.cu` | ✅ 已移植（注释级） | — |
| `src/ops/sparse_moe/prefill/sparse_moe_prefill_kernels.cu` | ✅ 已移植 | MoE prefill −15.9%（**该 artifact 为 dense，不触发**） |
| `src/ops/kernel/gqa_attention_decode.cuh` | ❌ **未移植** | **GQA decode kernel −38.8%**（6.5–7k ctx / 6 query token） |
| `src/ops/launcher/gqa_attention_decode.cu` | ❌ **未移植** | 同上（host 侧镜像 cap） |
| `bench/ops/rope_bench.cu` | ❌ 未移植 | 仅影响 bench 的路由标签 |
| `tests/ops/test_gqa_attention.cpp` | ❌ 未移植 | 上游为此改动补的数值 oracle |

另有两处**基底自有**的 170 字面量，由本次融合一并修正（不在 UDP 提交内）：
`src/ops/launcher/rmsnorm.cu`（预取门控阈值 170）与 `src/ops/linear_attention/…/output.cu` 的 CTA 目标数。

**缺口的影响量化**：`gqa_attention_decode` 是**解码**路径。上游实测在 6.5–7k 上下文、6 query token 的窗口下，单核 **−38.8%**——这正是长会话「追问/短续写」的典型形状。本端到端 A/B 中解码仅测了浅上下文 MTP3（进出 1.2% 噪声），**因此没有覆盖到该缺口的收益，也就没有暴露出来**。

### 3.3 P3 — CLI 兼容层（**已融合并端到端实测**）

**做法**：在 `src/serve/serve_options.cpp` 接受 Tensorninja 拼写的参数，映射到本构建的等效机制，其余接受并忽略并打印 note。覆盖 8 组：

| TN 拼写 | 本构建处理 |
|---|---|
| `--prefix-checkpoint-policy rolling-tool` | → `--auto-long-anchors 2`（生效，实测 `auto_long_anchors=2`） |
| `--prefix-checkpoint-policy stable-turn` | 接受（语义等于默认） |
| `--continuation-cache l1-l2-l3` | 接受 → 运行 l1-l2，打印「无 L3 磁盘层」note |
| `--continuation-cache l1-l2` | 接受（即本构建默认） |
| `--continuation-cache l1` / `off` | → 关闭 host 层 / 关闭前缀复用 |
| `--continuation-cache-dir` / `-namespace` | 接受并忽略（无磁盘层） |
| `--continuation-cache-l2-mib` | → `--host-kv-mib`（生效，实测 `host_kv_bytes=16 GiB`） |
| `--continuation-cache-l1-mib` / `-l3-mib` / `-filesystem-reserve-mib` / `-*-idle-seconds` / `-*-ttl-seconds` / `-persist-*` | 接受并忽略（device 池按空闲显存自动定尺） |

**实测**：用生产容器 `qwen38` 的**原始命令行逐字节**启动本镜像 → 启动成功、`/health` 200、推理冒烟通过、3 条 note 正确打印、映射确实生效（见端到端报告 §5）。**用户既有脚本无需改动。**

### 3.4 放弃项

| 项 | 原因 |
|---|---|
| L3 磁盘层 | 本构建以 `--slot-save-path` + `--auto-save-evicted` 覆盖跨重启会话复用（约 0.1 s 恢复 vs 数秒重预填充）；且无对应物理存储契约，硬移植风险高于收益 |
| Web UI / telemetry | 用户明确不需要 |
| NVFP4 / W4A4 | Ada 消费级卡无 FP4 张量核，不可用 |

## 4. 冲突与适配点（融合工程结论）

| 冲突类型 | 具体位置 | 处理 |
|---|---|---|
| **wrapper 手工合并** | `linear_swiglu` q4、`linear_add` q5、`attn_input_proj` q4_q5、`gdn_input_proj` q4_q5 的 4 个 wrapper | 基底多出 FP8 分支 → 保留基底分支 + 追加 Q4/Q5 允许 A8 |
| **基底缺陷：wrapper 忽略 policy** | `attn_input_proj` wrapper 的 q4/q5 分支 | 必须显式改为把 policy 透传，否则 A8 路线不生效 |
| **构建系统** | `src/CMakeLists.txt` 为**显式源文件列表**（非 glob） | 新增 6 条条目；漏一条即链接期或 configure 期失败 |
| **头文件 BOM** | `CMakeLists.txt` 曾被 BOM 污染 | 移植时踩过，构建 #2 失败；已在流程中固化检查 |
| **匿名参数** | `variant.cpp` 中 `attention_projection` 等 2 个函数的 `phase` 参数匿名 | 需先具名才能插入 policy 参数 |
| **constexpr 约束** | UDP 侧另有 `kTargetSmCount` 编译期镜像（用于 device 侧），基底无对应设施 | 本融合只移植 host 侧 `device_sm_count()`，device 侧镜像随 GQA 缺口一并待补 |

## 5. 端到端回顾：方案的验证与修正（review 结论）

### 5.1 已验证成立

| 结论 | 证据 |
|---|---|
| P2 INT8 预填充收益真实且显著 | 同参数 A/B：70K 深度 **1,507.7 → 2,325.2 tok/s（+54.2%）**；145K 深度 **1,228.8 → 1,751.8 tok/s（+42.6%）**；145K 提示词端到端墙钟 118.6 s → 98.6 s |
| 接口适配正确、无功能回归 | 长文 10,121 token 正常收尾；144K 上下文针探 `7391` 精确命中；CUDA 错误 0 |
| 移植内容只影响预填充 | 解码 144.4 → 146.1 tok/s（+1.2%，噪声内）—— 符合「只改 prefill 路线」的设计预期 |
| P3 兼容层可用 | 生产命令行逐字节实测通过，映射生效 |
| provenance 无损 | 9 个核心 INT8 文件与 TN **逐字节相同** |

### 5.2 需要修正的计划假设

**(1) P0a 不是崩溃修复。** 端到端测试中**基线同样完整跑完 GDN 长输出（13,474 token，0 CUDA 错误）**；上游提交自身也只描述为「partial straggler wave / 利用率」，并明确 `cudaDeviceGetAttribute` 查询得到 128 SM，网格 510 CTA 只有 384 常驻。→ P0a 应定位为**调优可移植性**，文档与提交信息不应声称修复了已观测的崩溃。

**(2) P0a 的收益被高估。** 上游逐点实测：MoE prefill −15.9%（**该 artifact 是 dense，不触发**）、rope −5…9%（**仅 769–1020 token 窄带**）、GDN chunked output **中性**。因此已融合的 P0a 部分对 `qwen3.8-27b` 的**实际贡献很小**；本端到端测得的 +43~54% 预填充增益，**主体应归因于 P2**（TN 单独声称 1.415×，与实测同量级）。这与「解码几乎不变」也自洽——若 P0a 真有大收益，解码侧（GQA decay 等）应可见变化。

**(3) P0a 覆盖不完整，且缺口正好是解码大项。** GQA attention decode 未移植（上游 **−38.8%**）。本 A/B 未覆盖该形状（浅上下文 MTP3），属于**测试盲区**，需补测。

**(4) 数值风险需显式验收。** 上游明示：改 split 划分会改变 **FP32 跨 split 归并顺序**，贪心续写可能在同一提示词上发散；上游为此补了 GQA oracle（window 7000 / 6 token / INT8）并验证旧 cap、新 cap、荒谬 cap=1 均通过。**本融合未移植该 oracle，也未跑 ops/CTest 套件**——这是当前最大的验收缺口。

**(5) 测试脚本自身缺陷。** 原 b) 用例的 1150 块提示词约 400K token，**超过 262,144 上限**被服务拒绝（`context_length_exceeded`）；已改为 200 块（≈70,221 token）。另：中文重复文本在此分词器下约 **1.57 字符/token**，按字符数估 token 会高估约 57%。

### 5.3 被证伪/排除的假设

| 假设 | 结论 |
|---|---|
| 「170 SM 硬编码会导致 cooperative launch 失败并崩溃」 | **未复现**；属 straggler wave 利用率问题 |
| 「P0a 是本轮预填充增益的主要来源」 | **不成立**；主体是 P2 |
| 「GDN chunked output 的 CTA 目标数需要修」 | 上游已验证**中性**（H_v=48、NT≤32 时 680 与 512 产出相同网格；引擎 1024 token chunk 即 NT=16）。修它只为消除最后一点 170 假设 |

## 7. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| split 划分变更 → FP32 归并顺序变化 | 贪心续写可能在同提示词上发散 | 移植 GQA oracle + ops/CTest；用针探与长文端到端做门禁 |
| GQA 缺口未补 | 长会话追问的解码收益（−38.8%）未取得；且留下不一致的 SM 假设 | P1 补齐 |
| 提示词按字符估 token | 触发 `context_length_exceeded` | 一律按服务端 `prompt_n` 计量 |
| 显存独占 | merged（24.8 GB）与 `qwen38`（~30 GB）不能共存 | 切换需停旧服务；E8 4-bit KV 可省约 4 GiB |
| MTP 接受率随内容波动 | 跨内容类型比 tok/s 失真 | A/B 必须同内容同参数 |
