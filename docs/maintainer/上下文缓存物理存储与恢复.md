# NInfer 上下文缓存物理存储与恢复

本文从物理资源视角描述 NInfer 上下文缓存的完整生命周期：显存/内存槽位的容量分配、
状态与 KV 在两级存储间的流转、驱逐与容量耗尽时的释放顺序、以及驱逐后的恢复路径。

它与 [resource-scheduling-and-context-cache.md](resource-scheduling-and-context-cache.md)
的关系：那篇定义规划算法与不变量（"谁可以驱逐谁、代价如何比较"）；本文聚焦
"数据实际住在哪、怎么搬、装不下时先丢谁、丢了怎么找回"。

---

## 1. 物理容量

NInfer 启动时按配置一次性建立以下固定容量（生产数值取自 `deploy-yarn/ninfer_service.sh`
与启动日志 `engine capacity …` / `engine state_pools …`）。

### 1.1 StateImage 槽位

StateImage 是 GDN 递归状态的完整快照（Qwen3.8-27B 约 147 MiB/份），**不可部分迁移**。

| 层级 | 配置项 | 生产值 | 说明 |
|---|---|---|---|
| 显存（Device） | `--device-state-slots` | 4（额外容量） | 活跃 lane 另需 1 份/条；`max-concurrency 4` ⇒ 共 8 份 ≈ 1.15 GiB |
| 内存（Host） | `--host-state-slots` | 320 | 完整 StateImage 的 CPU 侧副本，320 × 147 MiB ≈ 45.9 GiB |

两类槽位由同一个 `StateImageStore` 池管理，不与 lane 固定配对。启动门禁按
`host_state_slots × 147 MiB + host_kv + 4 GiB` 计算内存需求（生产约 83.9 GiB），
不足则拒绝启动，避免走到 "pinning host KV" 阶段被内核 OOM 杀掉。

### 1.2 KV 页

KV 以 256 token 为一页，分 Main KV（全注意力层）与 backend KV（MTP 层），各自独立寻址。

| 层级 | 配置项 | 生产值 | 说明 |
|---|---|---|---|
| 显存（Device） | `--kv-capacity` | `auto` | 按权重加载后的剩余显存计算；启动日志给出 `kv_capacity_tokens`、`kv_max_page_groups` 与 `text_kv_bytes`（约 10.7 GiB）、`mtp_kv_bytes`（约 0.7 GiB） |
| 内存（Host） | `--host-kv-mib` | 32768 | 32 GiB packed arena，页按 extent 分配 |

Host KV 由 `HostKVExtentStore` 以 packed extent 分配；显存 KV 页由逻辑页池 + 物理池管理。

### 1.3 逻辑容量

| 配置项 | 生产值 | 含义 |
|---|---|---|
| `--max-private-continuations` | 64 | private catalog slot 数（每个活跃/缓存会话占一个） |
| `--max-shared-prefixes` | 16 | shared prefix catalog slot 数 |
| `--max-long-anchors-per-continuation` | 16 | 单会话可保留的 long anchor 上限（实测会话通常只持有 2 个） |
| `--auto-long-anchors` / `--*anchor-spacing` | 32 / 8192, 32768 | 自动放置 long anchor 的数量与间距 |
| `--fair-share-buckets` | 8 | MRU 前 N 个空闲会话免于被选为 victim（0 禁用） |

> KV 地址空间描述符池 = `max_private_continuations + max_shared_prefixes + 1`（多出的 1 个
> 留给 in-flight active-capture 快照）。地址描述符本身只是簿记（每地址约 660 KB 的
> membership 表），真正受限的是 1.1/1.2 中的物理池。

## 2. 数据在两级存储间的流转

同一份 continuation 的 StateImage 与 KV 页可以分别驻留在任一层级：

```
┌─────────────────────────────────────────────────────────────────────┐
│  显存 (GPU HBM)                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────────────────┐ │
│  │ StateImage   │  │ KV pages     │  │ Active sequence (in-place) │ │
│  │ slots (8)    │  │ (Main+MTP)   │  │ (decode 推进中)            │ │
│  └──────────────┘  └──────────────┘  └───────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
         ▲ D2H / H2D                    ▲ H2D / D2H
┌─────────────────────────────────────────────────────────────────────┐
│  内存 (CPU, pinned)                                                 │
│  ┌──────────────┐  ┌──────────────────────────────────────────────┐ │
│  │ StateImage   │  │ Host KV arena (packed extents)               │ │
│  │ slots (320)  │  │ (Main KV + MTP KV 各自 extent)              │ │
│  └──────────────┘  └──────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.1 状态（StateImage）流转

| 操作 | 方向 | 触发时机 |
|---|---|---|
| InPlace | Device → Device | active decode 每 round 原地推进 |
| Move | Device → Device | 从 checkpoint consume 到 active（零拷贝，slot 复用） |
| Fork | Device → Device | 从 checkpoint 复制到新 slot（首次 state-write 前 pin source） |
| D2H (demote) | Device → Host | ① 压力规划降级 idle checkpoint；② 预留失败时的容量释放阶梯（见 4.2） |
| H2D (restore) | Host → Device | admission 选中 Host-resident checkpoint，需搬回显存 |
| Release | — | 最后引用消失，物理槽位归还 pool |

**降级的前提**：仅当该 state 是 `CheckpointImmutable`、已有（或本次可建立）Host 副本、
无 `source_pins` / `destination_pinned` / 进行中的传输时才可降级。
这一条曾长期失效，见 §4.4。

### 2.2 KV 页流转

| 操作 | 方向 | 说明 |
|---|---|---|
| 分配 | — | prefill/decode 增长时从 free list / arena 取页 |
| D2H (spill) | Device → Host | 压力规划将低价值 KV 页逐出到 Host arena |
| H2D (restore) | Host → Device | 恢复时从 Host extent 拷回 Device 页 |
| COW | Device → Device | partial-tail 页分叉（Fork 场景） |
| Release | — | refcount 归零时归还 free list / 释放 extent |

KV 页可以**部分在 Device、部分在 Host**（per-page 粒度）。一个 checkpoint 有效的前提是
每个 required page 至少有一份 Device 或 Host replica。

### 2.3 典型时序

```
会话 A 活跃 (decode)
  State: Device (in-place)     KV: Device (增长中)

会话 A 结束 (finish)
  State: Device checkpoint → 可能被压力规划降级到 Host
  KV:    Device → 可能被逐出到 Host

[其他会话挤占显存]

会话 B 到来，预留不到状态槽位
  容量释放阶梯：先降级一份保留状态到 Host；Host 也装不下则丢弃最老的空闲会话

会话 A 再次到来 (follow-up)
  catalog 仍覆盖其前缀 → H2D restore（State + KV）→ 亚秒继续
  catalog 不再覆盖        → root prefill 全量重算
```

## 3. 复用：两种命中路径

### 3.1 路径一：Catalog 命中（含 Host → Device 恢复）

```
请求 prompt → 计算 prefix digest
  → SessionIndex / catalog lookup → HIT
    → 定位 continuation slot（State/KV 在 Device 或 Host）
    → 若在 Host：H2D restore（整份 147 MiB state + 逐页 KV）
    → 从 checkpoint frontier 继续 prefill/decode
```

- 条件：该会话的 catalog 条目仍存在（其检查点覆盖请求前缀）
- 代价：Device-resident 时零拷贝；Host-resident 时约数 ms/份 state，实测端到端
  亚秒级 TTFT（见 §9 实测数据）

### 3.2 路径二：Root（全量重算）

```
请求 prompt → catalog MISS
  → root materialization: 从 token 0 完整 prefill
```

- 条件：catalog 中没有任何检查点覆盖该前缀，或数据从未被缓存
- 代价：完整 prefill（14K token ≈ 11 s，20K token ≈ 16 s）

### 3.3 路径选择

```text
                    新请求到达
                        │
                        ▼
              catalog / SessionIndex lookup
                  │              │
                HIT            MISS
                │              │
                ▼              ▼
        标准 materialization   root (全量 prefill)
        (H2D if Host-resident)
```

## 4. 驱逐与容量耗尽

### 4.1 Catalog 驱逐（逻辑层）

当新 continuation 需要 slot 而 catalog 已满时：

1. **压力规划**（materialization planner）选择 victim：候选是所有 inactive、无 active edge
   保护的 owner；保底桶内的会话被排除；准则是最小化 portfolio value 损失。
2. **执行驱逐**（`release_continuation_slot_strict`）：释放 catalog slot；数据是否留在物理池
   取决于它是否仍被引用（见 4.2）。

### 4.2 容量释放阶梯（预留失败时）

任何一次 StateImage 预留失败，都按**从省到狠**的顺序释放，而不是直接让请求失败：

```
release_state_capacity_step()
  ├─ release_one_device_state_slot()          # 腾出一个 Device 槽位
  │    ├─ ① 已有 Host 副本的保留状态：只丢弃 Device 副本（无需拷贝）
  │    ├─ ② DeviceOnly 的保留状态：D2H 拷到 Host arena → 发布副本 → 丢弃 Device 副本
  │    │     ② 因 Host 池满失败 → ②b 驱逐最老可驱逐锚点的 Host 副本
  │    │     （EvictHostReplica，pinned 锚点亦允许），腾出一个 Host 槽后重试 ②
  │    └─ ③ 无人绑定的状态：整体释放（被活会话绑定的状态受 §4.4 守卫保护）
  └─ retire_oldest_idle_continuation()        # 连 Host 容量都造不出来：丢弃最老的空闲会话
```

调用点（全部走这条阶梯，而不是抛错）：

| 场景 | 入口 |
|---|---|
| 私有状态目标 | `reserve_state_destination_with_release()` |
| Host 副本目标 | `reserve_logical_destination_with_release()` |
| HostOnly checkpoint 恢复 | materialization 的 state restore 分支 |
| active capture 的状态目标 | `prepare_active_capture` |
| 压力规划的 D2H 暂存 | `prepare_pressure_work` |

`retire_oldest_idle_continuation` 的选择依据是状态自身的 `last_touched_ns`（即该会话最近被
使用的时刻），无需额外的会话年龄记录；`freeze()` 会为新发布的 checkpoint 打上时间戳。

### 4.3 保底桶（Fair-share）

`fair_share_buckets`（默认 8）：

1. 所有无 active edge 的 catalog 会话按 last-activity epoch MRU 排序
2. 前 N 个构成"保底桶"，其 owner 从压力规划的 victim domain 中整体排除
3. 若共享池 + 全部非保护 owner 都耗尽、连 root 都不可行 → 释放最老保底桶重试
4. 保底桶是硬保证；与 retention weight 的软排序正交

### 4.4 关键不变量（两处曾长期失效，勿回退）

**① 降级选择器必须接受 DeviceOnly 状态。**
早期实现只挑选"同时持有 Device 与 Host 副本"的 state 作为降级对象。而常态下 checkpoint 要么
DeviceOnly（快速复用）、要么 HostOnly（慢速复用），两者只在传输途中短暂并存——于是选择器
永远选不出 sacrifice，Device 槽位永远释放不掉，最终表现为 `bad_alloc` → 500 → 后续请求 503。
现在的 `select_slot_release_victim` 明确区分"已有 Host 副本（只丢 Device 副本）"与
"DeviceOnly（先拷贝再丢）"两类，并由调用方真正执行 D2H 拷贝。

**② 释放前必须确认没有活会话仍绑定该状态。**
一个被冻结为 endpoint 的状态由序列**直接持有**，其 `checkpoint_references` 可以是 0；
仅凭引用计数判断"没人用"会释放掉活会话正在使用的状态，随后报
`checkpoint summary has a stale StateImage`。`state_bound_by_live_sequence` 检查所有非 Free
的 continuation（read/write/reserved/rewrite/long anchor）与 shared prefix 是否绑定该状态，
容量释放的"整体释放"一档以此作为否决条件。

**③ 被 pin 的锚点的 Host 副本必须可被驱逐（2026-09-21 修复）。**
旧实现里 victim 选择只认"持有 Device 槽"的对象，且 `Drop` 拒绝 pinned：Host 池一旦打满，
②的 D2H 拿不到 Host 槽、③又放不掉 pinned 锚点，Device 池便**永久不可恢复**——规划器的
静态峰值检查把所有需要 H2D 恢复的复用候选判为 `physical peak` 拒绝，全部回退 root 冷
prefill（实测：320 槽打满窗口内，8.5K 请求的复用从 98% 掉到 0%，TTFT 0.4 s → 7.1 s；
池子随后被价值模型慢慢腾开才恢复命中）。现在：②b（`EvictHostReplica`）允许丢弃最老锚点
的 Host 副本（pinned 亦可，`state_bound_by_live_sequence` 仍是否决条件），该锚点从此不可用
直至其 owner 重新发布，KV 页不受影响；同时规划器残差模型（`state_slot_relief`）把
"丢弃 Device 副本 / 降级 / 驱逐锚点"的救济计入 device-state，复用候选不再在规划阶段被
静态检查误杀。

## 5. 找回：驱逐后的恢复机制

### 5.1 Host → Device 恢复（正常路径）

Catalog 命中但数据在 Host 时：

```
H2D StateImage:  整份 147 MiB 拷贝到空闲 Device slot（PCIe 4.0 x16 约 5-10 ms）
H2D KV pages:    逐页从 Host extent 拷回 Device free list 分配的页
```

这是常规 materialization 的一部分，由 `ResourcePlan` 的 ordered stages 执行。
CPU 侧副本因此是"驱逐"与"恢复"之间唯一的桥梁：**只要条目还在、副本还在，恢复就是亚秒级。**

### 5.2 彻底丢失之后

若某会话的全部检查点都被驱逐，唯一路径是 **root prefill**：从 token 0 重算所有 KV 页与 GDN 状态。

**容量取舍**：catalog 条目数由 `--max-private-continuations` / `--max-shared-prefixes` 决定；
条目的物理数据由 Host StateImage 槽位与 Host KV arena 约束。两者共用同一笔内存额度，
因此"能记住多少会话"由额度决定，而不是由表的数量决定。想记住更多会话，应调大 catalog
上限并相应缩减每会话的 long anchor 数，而不是增加第二张索引表（见 §9）。

## 6. 容量规划

### 6.1 生产配置（32 GiB GPU + 91 GiB RAM）

```text
--device-state-slots 4          # + max-concurrency 4 = 8 份 Device StateImage
--host-state-slots 320          # ≈45.9 GiB Host StateImage
--host-kv-mib 32768             # 32 GiB Host KV arena
--kv-capacity auto              # 显存 KV 按剩余显存计算
--max-private-continuations 64
--max-shared-prefixes 16
--max-long-anchors-per-continuation 16 --auto-long-anchors 32
--fair-share-buckets 8
```

### 6.2 压测配置（小参数，便于触发驱逐）

```text
--device-state-slots 2  --host-state-slots 8  --host-kv-mib 512
--kv-capacity 32768     --max-private-continuations 4  --max-concurrency 2
--fair-share-buckets 2
```

更紧的临时配置（用于验证最坏情况）可再压到 `--host-state-slots 2 --device-state-slots 0
--kv-capacity 16384 --max-private-continuations 2 --fair-share-buckets 0`。

### 6.3 关键不等式

```text
可记住的会话数 ≈ min(host_state_slots, host_kv_arena_pages / pages_per_session)
                 （上限同时受 catalog slot 数约束）

当 并发/累计会话数 > 上式：
  - 数据在 Host → 回来时 H2D 恢复（亚秒）
  - 数据被释放 → root prefill（10s+）
```

| 日志标记 | 含义 |
|---|---|
| `[evict] slot=… frontier=… text_kv_valid=… ledger=… anchors=… endpoint=… state_valid=…` | 会话驱逐：端点前沿、KV 覆盖、token 账本长度、long anchor 数 |
| `[exhaust] drop oldest idle continuation slot=… age_ns=…` | 内存不足：丢弃最老的空闲会话 |
| `[state-store] D2H demote` / `D2H copy` | 状态从显存降级到内存（含槽位号） |
| `[state-store] anchor host evict handle=… host_slot=… pinned=…` | Host 池满：驱逐该锚点的 Host 副本腾槽（§4.4③）；`pinned>0` 时该锚点作废，待 owner 重新发布 |
| `[state-store] allocate FAILED role=… free_object=… free_device=…` + 槽位快照 | 状态池耗尽；随后打印每个占用者的 role/槽位/引用/pin 状态 |
| `[state-store] take_device_slot: NONE FREE` | Device 状态槽位耗尽（随后是快照） |
| `[stale] checkpoint_summary handle=… gen=… frontier=… kind=…` | 释放了不该释放的状态（500 前兆，见 §4.4②） |
| `[FATAL] slot_strict` / `[FATAL] release_*` | 释放路径发现真实不变量违例 → terminate |
| `[serve] EXCEPTION …` | serve 层捕获异常；消息带**抛出点标签**（如 `materialization state restore after LRU evict`） |

### 7.1 观察驱逐与恢复

```bash
grep -c "\[evict\] slot=" ninfer_serve.log        # 会话驱逐次数
grep -c "\[exhaust\]" ninfer_serve.log            # 内存不足丢弃最老的次数
grep -n "HTTP 500\|HTTP 503" ninfer_serve.log     # 可用性事件
grep "done | openai-chat" ninfer_serve.log | tail # 每请求 cache 比例与复用路径
```

"比首次快一半"这类启发式判据在首次基线已被预热时会误报。

## 9. 设计决策：不引入独立的恢复索引

曾经实现过一个"恢复索引"（`StateIndex`/`KVIndex`）：把被驱逐会话的 StateImage 与 KV 地址
空间按前缀指纹登记，回来时再"认领"回 catalog。它已被**整体移除**，依据是三条实测结论：

1. **它不增加容量。** 每条索引条目同样 pin 住一个 Host StateImage 槽位与一段 Host KV，
   与"把会话留在 catalog 里"花的是同一笔内存额度；能记住的会话数由额度决定。
2. **它在最需要的时候用不上。** 认领需要一个空闲 catalog 槽位（并经精确前缀校验），而会话
   被驱逐正是因为 catalog 满了；实测 26 次尝试中有 10 次因此直接返回。
3. **它的 pin 语义正是当日多次 500 的根因。** pin 让 `release()` 永远失败，从而占住 Device
   状态槽位与 KV 地址描述符直至池耗尽；索引驱逐还可能释放活会话仍在使用的状态。

移除后的对照实测（同一套负载）：

| 场景 | 移除前 | 移除后 |
|---|---|---|
| 20 对话 × 2000 词（生产，清缓存重启） | 5/5 HIT | **5/5 HIT**，缓存 99.3%，TTFT 0.26-0.37 s，0 错误 |
| 混合负载（9 种尺寸 + 反复切换 + 大对话回访） | 大对话回访 `cache 0%`、11-16 s 全量重算（FAIL） | **ALL TESTS PASSED**，0 驱逐、0 错误 |
| 压测配置 20+40 对话 | 依赖 pin 容错路径 | 70 请求 / 66 次驱逐 / 0 错误，RSS 稳定 3.77 GB |

也就是说：pin 造成的资源占用本身就在迫使检查点频繁换出——移除后压力显著下降
（`[exhaust]` 在常规与极紧配置下都不再触发），大对话回访也随之恢复正常。

### 11.3 锚点只在消息边界产生（重要）

自动锚点由前端按 `message_boundaries` 放置，且要求 `message_count > 1`
（`src/targets/qwen3_6/impl/frontend/frontend.cpp`）。因此：

- 单条 user 消息的请求**不会**产生任何内部锚点，无论 `--first-anchor-spacing` 多小；
- 要观察锚点与"中段恢复"，测试必须发**多轮对话**。

候选与保留策略（2026-09 修订，修复长对话分叉 0 命中）：

- 自动长锚点候选只取**用户消息之后的边界（用户轮起点）**：私有会话的分叉/回访/改写都发生在
  用户轮，工具循环内部边界没有请求会停下，若入候选会灌满预算、把真正有用的用户轮锚点挤掉
  （实测事故：16 个锚点全挤在最近 ~40k 的工具消息密集区，119k 处的分叉 0 命中、重算 119k）。
  `--auto-anchor-spacing` 间距骨干保持不变，覆盖长 prompt 与无用户轮的区域。
- 满额保留不再"替换最浅"：改为抽掉使锚点集最接近**等间距**的那个（间距平方偏差最小），
  并钉住最浅头锚；若新锚点冗余（不抽已更均匀）则跳过不发布。锚点集因此大致等距铺满整个
  会话跨度，老消息保留恢复点，尾部由实时端点覆盖。

实测（生产配置，20 条单轮 + 20 条 8 轮对话）：单轮对话的驱逐行一律 `anchors=0`；
多轮对话则出现 `anchors=6` 等取值，且被 20 条新会话挤出后回访仍是 **100% 缓存 / 0.25 s**。

### 11.4 内存利用实测

| 配置 | 负载 | 结果 |
|---|---|---|
| 生产（catalog 16+8，锚点 8192/32768） | 30 条单轮 2000 词 | 驱逐 29 次；峰值 **host_state 42/320（13%）、host KV 0 MiB**；500/503 = 0 |
| 生产（catalog 64+16，锚点 8192/32768） | 60 条 4 轮对话 | 峰值 **host_state 227/320（71%）**、device_state 8/8、host KV 0 MiB；3/3 回访命中 99.5%、17 次驱逐、0 错误 |
| 生产（catalog 64+16，锚点 512/1024） | 150 条 4 轮对话 | 峰值 **host_state 246/320（77%）**、87 次驱逐、anchors 峰值 2、0 错误 |
| 压测（锚点间距 100、单会话锚点 32） | 12 条 6 轮对话 + 10 条施压 | **21 次驱逐**、host_state 8/8 打满、anchors 4、0 错误；回访全 MISS（内存确实不够，符合"丢最老"预期） |

每个被跟踪会话的实际开销（由 246/64 反推）：**约 3.8 个 Host 状态槽 ≈ 560 MiB**（端点 + 约 2 个
锚点 + 工作副本）。据此，catalog 上限与 Host 状态池的关系是：16 → 13%、64 → 71-77%、
80 → 约 94%、96 以上会被 320 槽的池子上限卡住。

结论：catalog 从 16+8 抬到 64+16 后，Host 池在 60/150 会话负载下的峰值从约 13% 升到 71–77%，
已分配的内存因此被真正用起来。限制"能记住多少会话"的仍不是内存额度，而是 catalog 上限
（64；继续抬高到约 80 后池子即逼近上限，需同步缩减每会话锚点数）与会话内的检查点数量
（锚点只在消息边界、且需多轮）。Host KV 基本为 0：短会话的 KV 常驻显存，32 GiB arena
是长会话的保险。想记住更多会话，应抬高 catalog 上限并相应缩减每会话锚点数，
而不是增加新的索引结构（见 §9）。
