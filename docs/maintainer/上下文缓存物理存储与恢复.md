# NInfer 上下文缓存物理存储与恢复

本文从物理资源视角描述 NInfer 上下文缓存的完整生命周期：显存/内存槽位的容量分配、
状态与 KV 在两级存储间的流转、驱逐策略、以及驱逐后的查找与恢复路径。

它与 [resource-scheduling-and-context-cache.md](resource-scheduling-and-context-cache.md)
的关系：那篇定义规划算法与不变量（"谁可以驱逐谁、代价如何比较"）；本文聚焦
"数据实际住在哪、怎么搬、丢了怎么找回来"。

---

## 1. 物理容量

NInfer 启动时根据配置建立以下固定容量：

### 1.1 StateImage 槽位

StateImage 是 GDN 递归状态的完整快照（Qwen3.8-27B 约为 147 MiB/份）。

| 层级 | 配置项 | 默认/生产值 | 说明 |
|---|---|---|---|
| 显存（Device） | `device_state_slots` | 8（= max_concurrency） | 前 N 个 slot 保证 active request 独占；额外 slot 供 checkpoint 驻留 |
| 内存（Host） | `host_state_slots` | 320（生产）/ 8（压测） | 完整 StateImage 的 CPU 侧副本 |

Device 总容量 = `max_concurrency + device_state_slots`（若 `device_state_slots` 已包含
concurrency 则直接使用该值）。所有 slot 由同一个 `StateImageStore` 池管理，不与 lane
固定配对。

### 1.2 KV 页

KV 以 256 token 为一页，分为 Main KV（全注意力层）和 backend KV（MTP 层），各自独立
寻址空间。

| 层级 | 配置项 | 默认/生产值 | 说明 |
|---|---|---|---|
| 显存（Device） | 由 `kv_capacity` 隐式决定 | — | GPU HBM 中可分配的 KV 页总数 |
| 内存（Host） | `host_kv_mib` | 32768 MiB（生产）/ 512 MiB（压测） | CPU 侧 packed arena 总容量 |

Host KV arena 使用 packed extent allocator；显存 KV 页由 `KVAddressSpaceStore` 的
per-pool free list 管理。

### 1.3 逻辑容量

| 配置项 | 含义 |
|---|---|
| `max_private_continuations` | private catalog slot 总数（每个活跃/缓存会话占一个） |
| `max_shared_prefixes` | shared prefix catalog slot 总数 |
| `max_long_anchors_per_continuation` | 每条会话可保留的 long anchor checkpoint 上限 |
| `fair_share_buckets` | 保底桶数：MRU 排序后前 N 个空闲会话不被驱逐（默认 8，0 禁用） |

## 2. 数据在两级存储间的流转

一个 continuation 的 StateImage 和 KV 页可以独立存在于 Device 或 Host 任一层级：

```
┌─────────────────────────────────────────────────────────────────────┐
│  显存 (GPU HBM)                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────────────────┐ │
│  │ StateImage   │  │ KV pages     │  │ Active sequence (in-place) │ │
│  │ slots (N)    │  │ (Main+MTP)   │  │ (decode 推进中)            │ │
│  └──────────────┘  └──────────────┘  └───────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
         ▲ D2H / H2D                    ▲ H2D / D2H
┌─────────────────────────────────────────────────────────────────────┐
│  内存 (CPU)                                                         │
│  ┌──────────────┐  ┌──────────────────────────────────────────────┐ │
│  │ StateImage   │  │ Host KV arena (packed extents)               │ │
│  │ slots (M)    │  │ (Main KV + MTP KV 各自 extent)              │ │
│  └──────────────┘  └──────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.1 状态（StateImage）流转

| 操作 | 方向 | 触发时机 |
|---|---|---|
| InPlace | Device → Device | active decode 每 round 原地推进 |
| Move | Device → Device | 从 checkpoint consume 到 active（零拷贝，slot 复用） |
| Fork | Device → Device | 从 checkpoint 复制到新 slot（首次 state-write 前 pin source） |
| D2H (demote) | Device → Host | 压力规划决定将 idle checkpoint 从显存降级到内存 |
| H2D (restore) | Host → Device | admission 选中一个 Host-resident checkpoint，需搬回显存 |
| Release | — | 最后引用消失，物理内存归还 pool |

StateImage 是**完整迁移单位**：不做部分层 D2H，要么整份在 Device，要么整份在 Host。

### 2.2 KV 页流转

| 操作 | 方向 | 说明 |
|---|---|---|
| 分配 | — | prefill/decode 增长时从 free list / arena 取页 |
| D2H (spill) | Device → Host | 压力规划将不可达/低优先级 KV 页逐出到 Host arena |
| H2D (restore) | Host → Device | 恢复时从 Host extent 拷回 Device 页 |
| COW | Device → Device | partial-tail 页分叉（Fork 场景） |
| Release | — | refcount 降为零时归还 free list / 释放 extent |

KV 页可以**部分在 Device、部分在 Host**（per-page 粒度）。一个 checkpoint 有效要求
每个 required page 至少有一份 Device 或 Host replica。

### 2.3 典型时序

```
会话 A 活跃 (decode)
  State: Device (in-place)
  KV:    Device (增长中)

会话 A 结束 (finish)
  State: Device (checkpoint) 或 → Host (若压力规划 D2H)
  KV:    Device 或 → Host

[时间流逝，其他会话挤占显存]

会话 B 到来，需要显存
  压力规划: 驱逐会话 A 的 KV 页 (D2H) 和/或 StateImage (D2H)
  会话 A 的 catalog entry 被释放（slot 归还）

会话 A 再次到来 (follow-up)
  路径 1: catalog 仍有 entry → 直接 H2D restore → 继续
  路径 2: catalog 已驱逐 → StateIndex/KVIndex adopt → 重建
```

## 3. 复用：三种命中路径

当新请求到来时，系统按以下优先级尝试复用：

### 3.1 路径一：Catalog 直接命中（最理想）

```
请求 prompt → 计算 prefix digest
  → SessionIndex / catalog lookup → HIT
    → 找到 continuation slot（State+KV 仍在 Device 或 Host）
    → 若 State/KV 在 Host: H2D restore
    → 从 checkpoint frontier 继续 prefill/decode
```

- 条件：continuation 的 catalog slot 仍被占用（未被驱逐）
- 代价：Host-resident 时需 H2D 传输（~数 ms）；Device-resident 时零拷贝

### 3.2 路径二：StateIndex/KVIndex Adopt（驱逐后恢复）

```
请求 prompt → 计算 prefix digest
  → catalog lookup → MISS（会话已被驱逐）
  → StateIndex.lookup(digest) → HIT (StateImage 仍在 Host/Device)
  → KVIndex.lookup(digest) → HIT (KV 页仍在 Host/Device)
  → 分配空闲 catalog slot
  → 重建 SequenceState (ledger, prefix_identity, KV bundle)
  → 释放 index_pin / pin_count
  → 走标准 materialization 流程 (H2D if needed)
  → 继续
```

- 条件：catalog 驱逐了会话，但 StateIndex/KVIndex 的 pin 仍保留着物理数据
- 代价：需重建逻辑结构（~µs），若数据在 Host 仍需 H2D
- **关键价值**：避免了从 token 0 全量 re-prefill（10s+ → 亚秒）

### 3.3 路径三：Root（全量重算，最差）

```
请求 prompt → catalog MISS → StateIndex MISS → KVIndex MISS
  → root materialization: 从 token 0 开始完整 prefill
```

- 条件：StateIndex/KVIndex 中的条目也被驱逐了（索引容量满），或数据从未被缓存
- 代价：完整 prefill（长上下文可达 10s+）

### 3.4 路径选择流程

```text
                    新请求到达
                        │
                        ▼
              catalog / SessionIndex lookup
                  │              │
                HIT            MISS
                │              │
                ▼              ▼
        正常 materialize   StateIndex.lookup(digest)
                              │              │
                            HIT            MISS → root (全量 prefill)
                            │
                            ▼
                     KVIndex.lookup(digest)
                         │              │
                       HIT            MISS → root (全量 prefill)
                         │
                         ▼
                  try_adopt_from_index
                  (重建 + 释放 pin)
                         │
                         ▼
                  标准 materialization
                  (H2D if Host-resident)
```

## 4. 驱逐

### 4.1 Catalog 驱逐（逻辑层）

Private/shared catalog slot 数量有限。当新 continuation 需要 slot 而 catalog 已满时：

1. **压力规划**（materialization planner）选择 victim：
   - 候选：所有 inactive、无 active edge 保护的 owner
   - 排除：保底桶（`fair_share_buckets` 内 MRU 靠前的会话）
   - 准则：最小化 portfolio value 损失（retention weight × 未来复用概率）
2. **执行驱逐**：
   - 释放该 owner 的 catalog slot
   - 其 StateImage 和 KV 页的物理副本**不一定立即释放**（见 4.2）
   - 触发 D2H 降级（若数据还在 Device）

### 4.2 StateIndex/KVIndex Pin 保护（物理层）

Catalog 驱逐 ≠ 物理数据消失。StateIndex 和 KVIndex 通过 pin 机制独立保护物理副本：

| 组件 | Pin 字段 | 保护对象 |
|---|---|---|
| StateIndex | `index_pin`（StateImageStore::Object 上的独立计数） | 完整的 StateImage（Device 或 Host slot） |
| KVIndex | `pin_count`（KVAddressSpaceStore::Address 上的独立计数） | 具体的 KV 页 |

**为什么需要独立 pin：** 如果复用 `checkpoint_references`（state）或常规 refcount（KV），
索引引用会污染状态独占性判断和 active entitlement 计算，导致 `can_release` 误判、
active request 的 Fork/Move 决策出错。

**Pin 的释放时机：**
- Adopt 成功：`try_adopt_from_index` 释放 pin，所有权转交新 catalog slot
- 索引条目自身被驱逐：释放该条目持有的所有 pin
- Engine 关闭：全部释放

**Pin 对释放路径的影响：**
- `*_strict` release 函数遇到 pinned 对象时**跳过**（不释放物理资源），不崩溃
- 若 `can_release_ignoring_pin()` 也返回 false → 真正的 invariant 违规 → `[FATAL]` + `std::terminate()`
- `index_pin` 不阻止 D2H 降级（`can_release_after_checkpoint_references` 不检查 index_pin）

### 4.3 StateIndex/KVIndex 自身驱逐

索引容量有限（开放寻址哈希表，固定桶数）。满时：

- 按 `rebuild_cost × recency` 权重淘汰最低分条目
- 被驱逐条目的 pin 释放 → 若该 pin 是最后一个引用，物理数据真正释放
- 此后同一前缀的再请求将走 root 全量重算

### 4.4 保底桶（Fair-share）

`fair_share_buckets`（默认 8）：

1. 所有无 active edge 的 catalog 会话按 last-activity epoch MRU 排序
2. 前 N 个构成"保底桶"
3. 保底桶内的 owner 从压力规划的 victim domain 中**整体排除**
4. 若共享池 + 全部非保护 owner 都耗尽、连 root 都不可行 → 释放最老保底桶重试
5. 保底桶释放后，会话下次活动会重新进入 MRU 排序

保底桶是硬保证（"不可被牺牲"），与 retention weight 的软排序（"可行时牺牲谁"）正交。

## 5. 找回：驱逐后的恢复机制

### 5.1 Host → Device 恢复（正常路径）

Catalog 命中但数据在 Host 时：

```
H2D StateImage:  整份 147 MiB 拷贝到空闲 Device slot（~5-10 ms on PCIe 4.0 x16）
H2D KV pages:    逐页从 Host extent 拷回 Device free list 分配的页
```

这是常规 materialization 的一部分，由 `ResourcePlan` 的 ordered stages 执行。

### 5.2 StateIndex/KVIndex Adopt（驱逐后重建）

当 catalog 已驱逐但物理数据被索引 pin 保留时：

1. **查找**：`try_adopt_from_index(prompt, digests)` 从 prompt 末尾向前搜索
   （步长 1024 token，最小 frontier 1024），逐位置查询 StateIndex + KVIndex
2. **双重命中**：State 和 KV 必须在**同一 frontier** 都有完整条目
3. **重建**：分配空闲 catalog slot，重建 `SequenceState`（token ledger、prefix identity、
   KV address bundle、long anchors 列表）
4. **移交**：释放 index_pin / pin_count，返回 `AdoptResult{handle, frontier}`
5. **标准流程**：ResourceManager 包装为 `CheckpointRef`，走 `inspect_admission` →
   materialization（若需 H2D）→ execution

**与直接 H2D 的区别**：Adopt 多了一步逻辑结构重建（~µs 级 CPU 开销），但避免了
catalog slot 占用期间的长期 pin，使索引容量可以服务更多历史会话。

### 5.3 彻底丢失后的恢复

若 StateIndex/KVIndex 条目也被驱逐（物理数据释放），唯一恢复路径是 **root prefill**：
从 token 0 重新计算所有 KV 页和 GDN 状态。对于 100k+ token 的长会话，这意味着
10 秒以上的 TTFT。

**设计取舍**：索引容量 vs 内存占用。生产环境（320 host state slots + 32 GiB host KV）
的索引容量远大于 catalog 容量，绝大多数被 catalog 驱逐的会话可在索引中找到；极端内存
压力下（压测配置：8 host slots + 512 MiB KV），索引容量有限，部分会话会彻底丢失。

## 6. 容量规划指南

### 6.1 生产配置（32 GiB GPU + 大内存）

```
device_state_slots = 8       # 覆盖 max_concurrency
host_state_slots   = 320     # 大量历史会话的 State 驻留内存
host_kv_mib        = 32768   # 32 GiB 内存 KV arena
kv_capacity        = 32768   # 显存 KV 页上限 (32768 × 256 = 8M tokens)
max_private_continuations = 64
fair_share_buckets = 8
```

此配置下 catalog (64 slots) 远小于 host state capacity (320)，绝大多数被 catalog
驱逐的会话在 Host 上仍有完整 State+KV 副本，StateIndex/KVIndex adopt 成功率极高。

### 6.2 压测配置（小参数）

```
device_state_slots = 2       # 极小显存状态池
host_state_slots   = 8       # 仅 8 份内存 State
host_kv_mib        = 512     # 极小内存 KV
kv_capacity        = 32768
max_private_continuations = 4
max_concurrency    = 2
fair_share_buckets = 2
```

此配置下 8 个并发会话超出 4 个 catalog slot + 8 个 host slot 的总容量，
大量驱逐不可避免；512 MiB host KV 只能容纳少量页。用于验证：
- 驱逐路径无崩溃
- Pin-tolerant release 正确处理
- D2H 降级不阻塞
- 有限索引容量下的 graceful degradation（部分会话彻底丢失 → root prefill）

### 6.3 关键不等式

```
有效缓存容量 ≈ min(host_state_slots, host_kv_arena_pages / pages_per_session)

当 并发会话数 > 有效缓存容量 时：
  - 超出部分被驱逐
  - 若 StateIndex/KVIndex 仍有 pin → adopt 恢复（亚秒）
  - 若索引也满了 → root prefill（10s+）
```

## 7. 诊断与日志

| 日志标记 | 含义 |
|---|---|
| `[adopt] HIT` | StateIndex/KVIndex adopt 成功，会话从索引恢复 |
| `[adopt] MISS` | 索引查找失败，退回 root prefill |
| `[FATAL] slot_strict` | `release_continuation_slot_strict` 发现非 pin 原因的不可释放 → terminate |
| `[FATAL] materialization victim` | materialization victim 不可释放 → throw |
| `[can_release_strict] FAIL` | 诊断：具体哪个条件不满足 |
| `[serve] EXCEPTION` | serve 层 catch 到异常（500 前兆） |

### 7.1 监控 adopt 成功率

```bash
grep -c "\[adopt\] HIT" ninfer_serve.log
grep -c "\[adopt\] MISS" ninfer_serve.log
# HIT / (HIT + MISS) = 驱逐后恢复率
```

理想值：生产环境 > 95%（host 容量充足）；压测环境取决于索引容量。
