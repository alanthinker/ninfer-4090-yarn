# NInfer 上下文缓存物理存储与恢复

本文从物理资源视角描述 NInfer 上下文缓存的完整生命周期：显存/内存槽位的容量分配、
状态与 KV 在两级存储间的流转、驱逐与容量耗尽时的释放顺序、以及驱逐后的恢复路径。

它与 [resource-scheduling-and-context-cache.md](resource-scheduling-and-context-cache.md)
的关系：那篇定义规划算法与不变量（"谁可以驱逐谁、代价如何比较"）；本文聚焦
"数据实际住在哪、怎么搬、装不下时先丢谁、丢了怎么找回"。

---

## 1. 物理容量

NInfer 启动时按配置一次性建立以下固定容量（生产数值取自 `deploy/ninfer_service.sh`
与启动日志 `engine capacity …` / `engine state_pools …`）。

### 1.1 StateImage 槽位

StateImage 是 GDN 递归状态的完整快照（Qwen3.8-27B 约 147 MiB/份），**不可部分迁移**。

| 层级 | 配置项 | 生产值 | 说明 |
|---|---|---|---|
| 显存（Device） | `--device-state-slots` | 4（额外容量） | 活跃 lane 另需 1 份/条；`max-concurrency 4` ⇒ 共 8 份 ≈ 1.15 GiB |
| 内存（Host） | `--host-state-slots` | 320 | 完整 StateImage 的 CPU 侧副本，320 × 147 MiB ≈ 45.9 GiB |

两类槽位由同一个 `StateImageStore` 池管理，不与 lane 固定配对。启动门禁按
`host_state_slots × 147 MiB + host_kv + 4 GiB` 计算内存需求（生产约 83.9 GiB），
不足则拒绝启动，避免走到 "pinning host KV" 阶段被内核 OOM 杀掉。

### 1.2 KV 页

KV 以 256 token 为一页，分 Main KV（全注意力层）与 backend KV（MTP 层），各自独立寻址。

| 层级 | 配置项 | 生产值 | 说明 |
|---|---|---|---|
| 显存（Device） | `--kv-capacity` | `auto` | 按权重加载后的剩余显存计算；启动日志给出 `kv_capacity_tokens`、`kv_max_page_groups` 与 `text_kv_bytes`（约 10.7 GiB）、`mtp_kv_bytes`（约 0.7 GiB） |
| 内存（Host） | `--host-kv-mib` | 32768 | 32 GiB packed arena，页按 extent 分配 |

Host KV 由 `HostKVExtentStore` 以 packed extent 分配；显存 KV 页由逻辑页池 + 物理池管理。

### 1.3 逻辑容量

| 配置项 | 生产值 | 含义 |
|---|---|---|
| `--max-private-continuations` | 64 | private catalog slot 数（每个活跃/缓存会话占一个） |
| `--max-shared-prefixes` | 16 | shared prefix catalog slot 数 |
| `--max-long-anchors-per-continuation` | 16 | 单会话可保留的 long anchor 上限（实测会话通常只持有 2 个） |
| `--auto-long-anchors` / `--*anchor-spacing` | 5 / 4096, 32768 | 自动放置 long anchor 的数量与间距（锚点落在 user 消息之前；步长 = first-spacing 按 prompt 长度缩放，下限 1024） |
| `--fair-share-buckets` | 8 | MRU 前 N 个空闲会话免于被选为 victim（0 禁用） |

> KV 地址空间描述符池 = `max_private_continuations + max_shared_prefixes + 1`（多出的 1 个
> 留给 in-flight active-capture 快照）。地址描述符本身只是簿记（每地址约 660 KB 的
> membership 表），真正受限的是 1.1/1.2 中的物理池。

## 2. 数据在两级存储间的流转

同一份 continuation 的 StateImage 与 KV 页可以分别驻留在任一层级：

```
┌─────────────────────────────────────────────────────────────────────┐
│  显存 (GPU HBM)                                                     │
│  ┌──────────────┐  ┌──────────────┐  ┌───────────────────────────┐ │
│  │ StateImage   │  │ KV pages     │  │ Active sequence (in-place) │ │
│  │ slots (8)    │  │ (Main+MTP)   │  │ (decode 推进中)            │ │
│  └──────────────┘  └──────────────┘  └───────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
         ▲ D2H / H2D                    ▲ H2D / D2H
┌─────────────────────────────────────────────────────────────────────┐
│  内存 (CPU, pinned)                                                 │
│  ┌──────────────┐  ┌──────────────────────────────────────────────┐ │
│  │ StateImage   │  │ Host KV arena (packed extents)               │ │
│  │ slots (320)  │  │ (Main KV + MTP KV 各自 extent)              │ │
│  └──────────────┘  └──────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.1 状态（StateImage）流转

| 操作 | 方向 | 触发时机 |
|---|---|---|
| InPlace | Device → Device | active decode 每 round 原地推进 |
| Move | Device → Device | 从 checkpoint consume 到 active（零拷贝，slot 复用） |
| Fork | Device → Device | 从 checkpoint 复制到新 slot（首次 state-write 前 pin source） |
| D2H (demote) | Device → Host | ① 压力规划降级 idle checkpoint；② 预留失败时的容量释放阶梯（见 4.2） |
| H2D (restore) | Host → Device | admission 选中 Host-resident checkpoint，需搬回显存 |
| Release | — | 最后引用消失，物理槽位归还 pool |

**降级的前提**：仅当该 state 是 `CheckpointImmutable`、已有（或本次可建立）Host 副本、
无 `source_pins` / `destination_pinned` / 进行中的传输时才可降级。
这一条曾长期失效，见 §4.4。

**降级不接受"活会话绑定"否决（2026-09-21 修复）。** 降级是非破坏性的（state 保留 Host 副本），
但它一度套用了保守的 `state_bound_by_live_sequence` 否决：空闲（Catalogued）会话仍把它保留的
锚点列在自己的 `long_anchors` 里，于是**所有空闲 owner 的 Device 驻留检查点都不可降级**，
阶梯腾不出 Device 槽，只能走最后一步退休整个空闲会话——保留量从 ~320 崩到 ~29（实测填充：
20 次退休 + 157 次驱逐，host 池停在 29/320；修复后同样负载 248/320、零退休零驱逐）。现在降级
只否决在途物化自己的 source（`release_protected_state`，见 §4.2）。

### 2.2 KV 页流转

| 操作 | 方向 | 说明 |
|---|---|---|
| 分配 | — | prefill/decode 增长时从 free list / arena 取页 |
| D2H (spill) | Device → Host | 压力规划将低价值 KV 页逐出到 Host arena |
| H2D (restore) | Host → Device | 恢复时从 Host extent 拷回 Device 页 |
| COW | Device → Device | partial-tail 页分叉（Fork 场景） |
| Release | — | refcount 归零时归还 free list / 释放 extent |

KV 页可以**部分在 Device、部分在 Host**（per-page 粒度）。一个 checkpoint 有效的前提是
每个 required page 至少有一份 Device 或 Host replica。

### 2.3 典型时序

```
会话 A 活跃 (decode)
  State: Device (in-place)     KV: Device (增长中)

会话 A 结束 (finish)
  State: Device checkpoint → 可能被压力规划降级到 Host
  KV:    Device → 可能被逐出到 Host

[其他会话挤占显存]

会话 B 到来，预留不到状态槽位
  容量释放阶梯：先降级一份保留状态到 Host；Host 也装不下则丢弃最老的空闲会话

会话 A 再次到来 (follow-up)
  catalog 仍覆盖其前缀 → H2D restore（State + KV）→ 亚秒继续
  catalog 不再覆盖        → root prefill 全量重算
```

## 3. 复用：两种命中路径

### 3.1 路径一：Catalog 命中（含 Host → Device 恢复）

```
请求 prompt → 计算 prefix digest
  → SessionIndex / catalog lookup → HIT
    → 定位 continuation slot（State/KV 在 Device 或 Host）
    → 若在 Host：H2D restore（整份 147 MiB state + 逐页 KV）
    → 从 checkpoint frontier 继续 prefill/decode
```

- 条件：该会话的 catalog 条目仍存在（其检查点覆盖请求前缀）
- 代价：Device-resident 时零拷贝；Host-resident 时约数 ms/份 state，实测端到端
  亚秒级 TTFT（见 §9 实测数据）

### 3.2 路径二：Root（全量重算）

```
请求 prompt → catalog MISS
  → root materialization: 从 token 0 完整 prefill
```

- 条件：catalog 中没有任何检查点覆盖该前缀，或数据从未被缓存
- 代价：完整 prefill（14K token ≈ 11 s，20K token ≈ 16 s）

### 3.3 路径选择

```text
                    新请求到达
                        │
                        ▼
              catalog / SessionIndex lookup
                  │              │
                HIT            MISS
                │              │
                ▼              ▼
        标准 materialization   root (全量 prefill)
        (H2D if Host-resident)
```

## 4. 驱逐与容量耗尽

### 4.1 Catalog 驱逐（逻辑层）

当新 continuation 需要 slot 而 catalog 已满时：

1. **压力规划**（materialization planner）选择 victim：候选是所有 inactive、无 active edge
   保护的 owner；保底桶内的会话被排除；准则是最小化 portfolio value 损失。
2. **执行驱逐**（`release_continuation_slot_strict`）：释放 catalog slot；数据是否留在物理池
   取决于它是否仍被引用（见 4.2）。

### 4.2 容量释放阶梯（预留失败时）

**契约（2026-09-22 明确）**：**启动参数保证的是工作集** —— 活跃请求自己需要的状态与 KV（`--max-concurrency` + `--device-state-slots`、`--kv-capacity`、以及活跃 lane 的 host 侧需求）。**其余全部是缓存**：缓存存在的意义只是让后续请求变快，因此**任何时刻都可以删**，唯一的要求是**挑出最没价值的那个**。据此：

- **不存在"空间不足所以拒绝"**：只要池里还有缓存（工作集之外），阶梯就必须能腾出槽位；
- 选谁删由**价值模型**决定：正常路径上由压力搜索用 `ContextPortfolioValue`（§调度文档）给每个 victim 集算价值损失、取损失最小者；紧急阶梯用"锚点优先、LRU 次之"作为价值代理；
- 只有在**剩下的全是活的东西**（活跃 lane、在途事务的 source/pin、pending 搬运）时，才可能出现真的腾不出来——那时请求退回 root 重算，而不是失败（见下）。

任何一次 StateImage 预留失败，都按**从省到狠**的顺序释放，而不是直接让请求失败：

```
release_state_capacity_step()
  ├─ release_one_device_state_slot()          # 腾出一个 Device 槽位
  │    ├─ ① 已有 Host 副本的保留状态：只丢弃 Device 副本（无需拷贝）
  │    ├─ ② DeviceOnly 的保留状态：D2H 拷到 Host arena → 发布副本 → 丢弃 Device 副本
  │    │     ② 因 Host 池满失败 → ②b 驱逐最老可驱逐锚点的 Host 副本
  │    │     （EvictHostReplica，pinned 锚点亦允许），腾出一个 Host 槽后重试 ②
  │    └─ ③ 无人绑定的状态：整体释放（被活会话绑定的状态受 §4.4 守卫保护）
  └─ retire_oldest_idle_continuation()        # 连 Host 容量都造不出来：丢弃最老的空闲会话
```

**阶梯的最后一档必须真的做得到（2026-09-22 修复）。** 满池的稳态是：Host 池里全是 HostOnly 检查点、Device 池里全是 DeviceOnly 检查点、**Both 驻留 0 个**。此时 ①②②b 三条全部因"要求冗余副本"而不合格，③ 又要求 `checkpoint_references == 0`（保留中的检查点一定被 owner 引用）——于是阶梯**没有任何被允许删除的东西**，复用被判不可行、请求退回 root 冷跑（生产实测：8,453 token 的复用被拒，重读 9,457 token / 8.8 秒；那 202 个检查点里 177 个 HostOnly 本是可删的）。两处修正：

- **退休空闲会话时释放它持有的共享前缀引用**（`release_active_shared_references_strict`），guard 改为**校验这些引用可释放**而不是"有引用就禁止退休"。此前"引用共享前缀"被当成活绑定，导致任何用过分共享前缀的会话都不可退休；
- 由于"删一个缓存"是真能做得到的动作，**规划器重新计入这份 relief**（仅当便宜手段已用尽时计入，且只记一个 owner 的量）。无条件计入曾在 2026-09-21 让"几乎每个请求都退休一个会话"、保留量 320→29，所以它必须是**有界**的。

**兑现不了就退回重算，绝不 500（2026-09-22）。** 计划封存后容量仍不足时，引擎回滚该次物化并把请求**放回候补队列**（`materialization: re-admit after progress capacity miss site=…`），下一次准入按 root 重算（`request->reuse_suppressed`）。计数进请求日志（`capacity re-plans N`）与引擎统计（`materialization_capacity_replans`），所以降级是**可见的**而不是静默的；连续 8 次仍不成才让该请求报错。为此 Program 在物化失败时**保留**已消费的 prompt（`take_failed_materialization_prompt`）——它是 move-only 的，丢掉它正是以前容量 miss 会以 `prepared prompt is empty` 变成 500 的原因。

调用点（全部走这条阶梯，而不是抛错）：

| 场景 | 入口 |
|---|---|
| 私有状态目标 | `reserve_state_destination_with_release()` |
| Host 副本目标 | `reserve_logical_destination_with_release()` |
| HostOnly checkpoint 恢复 | materialization 的 state restore 分支 |
| active capture 的状态目标 | `prepare_active_capture` |
| 压力规划的 D2H 暂存 | `prepare_pressure_work` |

`retire_oldest_idle_continuation` 的选择依据是状态自身的 `last_touched_ns`（即该会话最近被
使用的时刻），无需额外的会话年龄记录；`freeze()` 会为新发布的 checkpoint 打上时间戳。

**阶梯不得动在途物化的 source（2026-09-21 修复）。** `release_protected_state` 记录当前
materialization 正在恢复的状态，①②③ 与 `retire_oldest_idle_continuation` 的选择器一律跳过它。
否则阶梯会在"计划已按 Device 驻留定价"与"发布搬运"之间把源降级或退休，提交时报
`Host retained Fork destination was not published`（实测：计划通过、请求 500）。

**阶梯的能力必须被规划器如实计入，且只能计入做得到的部分。** 规划器的可行性判据
（`physical_peak_fits` / `materialization_deficit` / `guided_materialization_deficit`）通过
`state_slot_relief` 抵扣"阶梯还能腾出多少 Device 槽"：丢弃已有 Host 副本的 Device 副本、
把 DeviceOnly 降级（需要 Host 预算）、以及**阶梯最后一步退休最老空闲会话所释放的 Device/Host
槽**。两点约束：

- 计数用"**活跃绑定**"谓词（`state_bound_by_active_sequence`），而不是保守的
  `state_bound_by_live_sequence`：空闲（Catalogued）会话保留的锚点是**缓存**而非活绑定，
  保守谓词会把它们全部算作不可回收，于是满池时 relief 恒为 0，`physical_peak_fits` 以
  `state add=1 used=N cap=N` 拒掉所有 Host 驻留复用候选，请求退化成 root 冷跑
  （2026-09-21 生产事故：单发客户端的兄弟消息连续 0% 命中）；
- `host_evictable`（②b）只计**冗余** Host 副本（Both 驻留者）——驱逐 HostOnly 检查点的唯一副本会
  让它"没有已发布副本"（实测 500：`checkpoint StateImage has no published replica`）；
- **最后一步的退休不计入 credit**：退休是破坏性动作，把它计入会让规划器按"能退休会话"排计划，
  运行时随后销毁了活跃引用仍在使用的状态（实测 500：`StateImage handle is stale`）。需要容量的
  私有捕获改为**在预留时先回收、再按新状态重新评估**（见下），而不是让模型凭空承诺。

**私有捕获可以回收容量，共享晋升只能吃空余（2026-09-21 定案）。** 捕获发布的是请求**自己**的私有
检查点时，它就是 §6.2 里"不得被阻塞的 private baseline"：静态检查说不可行时，Program 先在预留处
走容量释放阶梯（降级、驱逐冗余 Host 副本、退休空闲会话），再重新评估，仍不可行才跳过。发布的是
纯共享晋升时，按 §7.2 只允许"不降低现有 owner 的空余容量"（阶梯不启用退休档）。这样满池
（host 320/320 + device 8/8 + KV 顶满）时，最新请求自己的锚点仍会发布：生产实测满池下
`capture: retry ... private-baseline-infeasible` → `capture: reserved ... host-snapshot`，
随后兄弟消息 `cache 7,811 (96.6%, long anchor)`、TTFT 0.44 s。

**计划引用的 owner 可能被阶梯退休，定价必须容忍。** 阶梯的最后一步可以退休一个空闲 owner，
而 ResourceManager 的 catalog 视图要等下一次重建才对齐；此时对该 owner 的检查点定价
（`checkpoint_recovery_work`）会抛 `StalePlanningReference`——其节省已不可实现，规划侧跳过该
检查点，预留侧返回 `MaterializationReserveResult::Stale` 让引擎重新规划，而不是把请求打成 500。

### 4.3 保底桶（Fair-share）

`fair_share_buckets`（默认 8）：

1. 所有无 active edge 的 catalog 会话按 last-activity epoch MRU 排序
2. 前 N 个构成"保底桶"，其 owner 从压力规划的 victim domain 中整体排除
3. 若共享池 + 全部非保护 owner 都耗尽、连 root 都不可行 → 释放最老保底桶重试
4. 保底桶是硬保证；与 retention weight 的软排序正交

### 4.4 关键不变量（两处曾长期失效，勿回退）

**① 降级选择器必须接受 DeviceOnly 状态。**
早期实现只挑选"同时持有 Device 与 Host 副本"的 state 作为降级对象。而常态下 checkpoint 要么
DeviceOnly（快速复用）、要么 HostOnly（慢速复用），两者只在传输途中短暂并存——于是选择器
永远选不出 sacrifice，Device 槽位永远释放不掉，最终表现为 `bad_alloc` → 500 → 后续请求 503。
现在的 `select_slot_release_victim` 明确区分"已有 Host 副本（只丢 Device 副本）"与
"DeviceOnly（先拷贝再丢）"两类，并由调用方真正执行 D2H 拷贝。

**② 释放前必须确认没有活会话仍绑定该状态。**
一个被冻结为 endpoint 的状态由序列**直接持有**，其 `checkpoint_references` 可以是 0；
仅凭引用计数判断"没人用"会释放掉活会话正在使用的状态，随后报
`checkpoint summary has a stale StateImage`。`state_bound_by_live_sequence` 检查所有非 Free
的 continuation（read/write/reserved/rewrite/long anchor）与 shared prefix 是否绑定该状态，
容量释放的"整体释放"一档以此作为否决条件。

**③ 被 pin 的锚点的 Host 副本必须可被驱逐（2026-09-21 修复）。**
旧实现里 victim 选择只认"持有 Device 槽"的对象，且 `Drop` 拒绝 pinned：Host 池一旦打满，
②的 D2H 拿不到 Host 槽、③又放不掉 pinned 锚点，Device 池便**永久不可恢复**——规划器的
静态峰值检查把所有需要 H2D 恢复的复用候选判为 `physical peak` 拒绝，全部回退 root 冷
prefill（实测：320 槽打满窗口内，8.5K 请求的复用从 98% 掉到 0%，TTFT 0.4 s → 7.1 s；
池子随后被价值模型慢慢腾开才恢复命中）。现在：②b（`EvictHostReplica`）允许丢弃最老锚点
的 Host 副本（pinned 亦可，`state_bound_by_live_sequence` 仍是否决条件），该锚点从此不可用
直至其 owner 重新发布，KV 页不受影响；同时规划器残差模型（`state_slot_relief`）把
"丢弃 Device 副本 / 降级 / 驱逐锚点"的救济计入 device-state，复用候选不再在规划阶段被
静态检查误杀。

**④ 满池时"最新请求自己的缓存"必须仍可命中（2026-09-21 修复）。**
③ 之后仍有第二个缺口：relief credit 用的保守谓词把空闲会话保留的锚点也算作活绑定，
于是**满池时 relief 恒为 0**，规划器再次以 `state add=1 used=N cap=N` 拒掉复用候选——而
这次运行时其实做得到（降级/退休空闲 owner）。实测该几何下：冷跑一条建立锚点 → 兄弟消息
`reuse offered 8,159 but planned from root (… reuse infeasible (physical peak status=1 rej=3
state add=1 used=4 cap=4))`，即**目录里有可用锚点却用不上**。修复见 §4.2 新增的三段：
活跃绑定谓词计 relief、把阶梯最后一步的退休能力也计入、用 `release_protected_state` 保护
在途物化的 source。修复后同一几何：兄弟消息 `cache 7,845 (96.5%, long anchor)`、TTFT
0.42 s，规划走无压力快速路径（1–2 个 target、0.1 ms）。

**⑤ 最新一条消息之前的边界必须留下 prefix-keyed 长锚点（2026-09-22 修复）。**
admission 会把相隔不足一个 `prefill_chunk` 的 capture frontier 合并，只留下间距内的代表；旧实现**从最浅
边界向后**合并，于是 5 段常量 + 一条 user 消息的线上形状（各块边界相隔仅 8–700 token）每次只剩
`{第一个锚点, 最深 closure}` 两个组——而最深边界上的 checkpoint 是 **turn closure**，其 shortlist digest
绑定本次 turn，兄弟消息一律 `digest-mismatch`。结果是每条消息只把可复用深度推进一个边界，实测连续兄弟
消息 89.3% → 95.9% → 96.9% → 99.9%（TTFT 864 → 515 → 463 → 151 ms），用户体感即"我发的消息没被缓存"。
现在合并**从最新边界向旧边界**计算并无条件保留最新边界之前的 long anchor（见规划文档 §7.1），冷跑一条
之后**第一条**兄弟消息即命中该锚点：生产配置实测 `cache 9,454 (99.8%, long anchor)`、TTFT 146–154 ms
（其中 queue 11 ms），小参数实例同样 99.8%。残差只剩本次最终消息自身的模板渲染（十余 token），不可
复用。

**⑦ 可选捕获的失败不得升级为引擎致命错误（2026-09-22 修复）。**
捕获（锚点/cloure/共享前缀）是**可选**的：§6.2 只保证"最新请求自己的私有检查点"，共享发布更是可选项。
但当时几条路径把它当成不变量：规划器选定的 shared 替换目标在预留前被阶梯退休（满池时很常见）→
`inspect_capture` 抛 `capture replacement capability is stale`；私有锚点替换目标同类；预留时
device/host 状态目的地一个也腾不出来 → 抛 `selected capture has no prepared Device State capacity`。
这些异常逃到 Engine worker 层触发 `fail_all_locked`：**清空全部会话状态并把引擎置为 failed**，此后每个
请求 503 直到重启（实测：满池下 21 条消息的分叉请求，服务直接不可用）。现在的处理：

- stale / 被活跃引用的 shared 替换目标 → 该场景"不可发布"（`publishes_shared=false`），
  assessment 继续按私有基线完成；RM 跳过该场景、Program 在预留时也会先校验并记
  `capture: degrade frontier=… reason=stale-shared-replacement`；
- stale 私有锚点替换目标（锚点集已满）→ 该组"不可发布"并被跳过，请求继续；
- device/host 状态目的地腾不出来 → `prepare_active_capture` 返回未就绪，调用方中止该次捕获并记
  `capture: skip frontier=… reason=state-destination-unavailable`，请求继续；
- `fail_all_locked` 仍作为最后的不变量兜底，但现在会把异常文本写进服务日志
  （`[engine] fatal: …`），不再只出现在 request log 的 `error.message` 里。

同一根因还有第二个出口（2026-09-22 第二次复现）：**捕获规划的 owner 映射必须对失效 owner 封闭**。
RM 用 catalog 视图构造 `capture_owner_records`（规划域），而 scenario/受害者列表也从同一视图枚举；
阶梯退休某个 owner 后，两边会不一致，于是 `owner_id_for()` 找不到规划 ID 并抛
`capture owner has no planning ID` —— 同样是致命。现在：

- 进入规划域前就用 `continuation_is_live` / `shared_prefix_is_live` 确认 owner 仍存在，
  不存在则就地清除 catalog entry（`catalog: clear retired private/shared owner slot=…`）并跳过；
- `owner_id_for()` 改为返回 `optional`：不在规划域内的 owner 只是"不是受害者"，从受害者列表里剔除；
- 若某个 shared 场景的替换目标已不在规划域内，该场景直接跳过并记
  `capture: skip frontier=… reason=replacement-not-plannable`，私有基线照常发布。


**⑧ 容量不足（而非不变量违例）不得升级为引擎致命错误（2026-09-22 修复）。**
请求自己的物化（复用）在"阶梯也腾不出容量"时抛 `SiteBadAlloc`，逃到 Engine worker 同样是
`fail_all_locked` → 清空全部会话 + 服务不可用。Program 的 `reserve_materialization` 在抛出前已经
`release_materialization_staging` 回滚了自己的暂存，因此这类失败是**可重试**的：现在 ResourceManager
把 `SiteBadAlloc` 与 `StalePlanningReference` 一样映射为 `MaterializationReserveResult::Stale`，
引擎重新规划（下一次规划看到阶梯刚产生的新池子，通常直接退回 root 冷 prefill）。日志记
`materialization: re-plan after capacity miss site=…`。

为避免"同一请求无限重规划"，引擎对每个请求的 `Stale` 重规划次数设上限（8 次）：超限时只让**该请求**
以明确原因失败（`[engine] request N gave up after M re-plans`），引擎继续服务。仍然致命的只剩真正的
不变量违例与未知来源的异常（如裸 `std::bad_alloc`、CUDA 错误）——它们意味着状态可能已损坏。

**⑥ catalog 里的 owner handle 必须在使用前确认 Program 侧仍存在。**
Program 在预留时回收容量会退休空闲 owner，这条路径不经过 ResourceManager 的 pressure transaction，
catalog 因此可能短暂保留已退休的 continuation。把它当复用 source 会让整条请求以
`admission source continuation is stale` 500（2026-09-22 harness：host=4/device=2 打满后每轮必现）。
现在 candidate 循环发现即 `clear_catalog_entry` / `clear_shared_entry` 并继续规划，日志
`catalog: clear retired private owner slot=… frontier=…`。

## 5. 找回：驱逐后的恢复机制

### 5.1 Host → Device 恢复（正常路径）

Catalog 命中但数据在 Host 时：

```
H2D StateImage:  整份 147 MiB 拷贝到空闲 Device slot（PCIe 4.0 x16 约 5-10 ms）
H2D KV pages:    逐页从 Host extent 拷回 Device free list 分配的页
```

这是常规 materialization 的一部分，由 `ResourcePlan` 的 ordered stages 执行。
CPU 侧副本因此是"驱逐"与"恢复"之间唯一的桥梁：**只要条目还在、副本还在，恢复就是亚秒级。**

### 5.2 彻底丢失之后

若某会话的全部检查点都被驱逐，唯一路径是 **root prefill**：从 token 0 重算所有 KV 页与 GDN 状态。

**容量取舍**：catalog 条目数由 `--max-private-continuations` / `--max-shared-prefixes` 决定；
条目的物理数据由 Host StateImage 槽位与 Host KV arena 约束。两者共用同一笔内存额度，
因此"能记住多少会话"由额度决定，而不是由表的数量决定。想记住更多会话，应调大 catalog
上限并相应缩减每会话的 long anchor 数，而不是增加第二张索引表（见 §9）。

## 6. 容量规划

### 6.1 生产配置（32 GiB GPU + 91 GiB RAM）

```text
--device-state-slots 4          # + max-concurrency 4 = 8 份 Device StateImage
--host-state-slots 320          # ≈45.9 GiB Host StateImage
--host-kv-mib 32768             # 32 GiB Host KV arena
--kv-capacity auto              # 显存 KV 按剩余显存计算
--max-private-continuations 64
--max-shared-prefixes 16
--max-long-anchors-per-continuation 16 --auto-long-anchors 5
--fair-share-buckets 8
```

### 6.2 压测配置（小参数，便于触发驱逐）

```text
--device-state-slots 2  --host-state-slots 8  --host-kv-mib 512
--kv-capacity 32768     --max-private-continuations 4  --max-concurrency 2
--fair-share-buckets 2
```

更紧的临时配置（用于验证最坏情况）可再压到 `--host-state-slots 2 --device-state-slots 0
--kv-capacity 16384 --max-private-continuations 2 --fair-share-buckets 0`。

### 6.3 关键不等式

```text
可记住的会话数 ≈ min(host_state_slots, host_kv_arena_pages / pages_per_session)
                 （上限同时受 catalog slot 数约束）

当 并发/累计会话数 > 上式：
  - 数据在 Host → 回来时 H2D 恢复（亚秒）
  - 数据被释放 → root prefill（10s+）
```

## 7. 诊断与日志

| 日志标记 | 含义 |
|---|---|
| `[evict] slot=… session=… frontier=… text_kv_valid=… ledger=… anchors=… endpoint=… state_valid=…` | 会话驱逐：被驱逐的 **session digest**（与 `/slots` 和客户端看到的同一个值，因此能直接对上"哪个对话死了"）、端点前沿、KV 覆盖、token 账本长度、long anchor 数 |
| `[evict-pick] owner=… slot=… kind=… class=… hits=… credit=… weight=… last_hit=… evidence=… risk=… score=… rank=…/… cheaper=… retained_cheaper=… unpriced=…` | 规划器**为什么**选它当受害者：`risk` 是该 owner 的价值在险（ns，未乘证据），`score = risk × evidence` 是联合受害者分（`materialization_victim_cost`，见 resource-scheduling-and-context-cache.md §8.3.1），`evidence` 是复用证据乘子（Q16，下限 0.125），`hits` 是 **owner 级生命周期复用次数**（自复用也计入，跨 checkpoint 替换保留）。`rank`/`cheaper` **只统计已定价的 owner**：`unpriced` 是本次规划里已被 Program 退休、因而没有任何可回收状态的 owner 数（它们的 0 分不代表"便宜"）。`cheaper=0` 表示联合序的最小值确实被选中，`retained_cheaper>0` 表示有更便宜的 owner 留在池里（不可靶向，或被 fair-share 保护）。活跃/被 pin/被 fair-share 保护的 owner 根本不在集合里，所以 `rank` 不是全池排名。`NINFER_EVICT_PICK=0` 关闭（默认开，因为整会话驱逐每小时只有几十次） |
| `[evict-pick]   kept-cheaper owner=… class=… hits=… credit=… weight=… evidence=… risk=… score=…` | 上面一行里**分数最低却活下来**的前 3 个 owner，用于直接对照"被杀的"和"留下的" |
| `[exhaust] drop oldest idle continuation slot=… age_ns=…` | 内存不足：丢弃最老的空闲会话 |
| `[ladder] retire site=… ok=… device=N/M` | 阶梯走到最后一步（退休整会话）的**入口点**与当时 Device 槽占用；`site` 区分 state-destination / logical-destination / state-restore / capture-destination。保留量异常时应先看这一行（2026-09-21：降级否决回归导致它几乎每请求出现） |
| `[ladder] no non-destructive capacity site=…` | 可选捕获（`allow_retire=false`）拿不到不破坏他人缓存的容量 → 该次捕获改为跳过（§7.2） |
| `[ladder] demote begin failed …` / `[ladder] drop_device_replica failed …` | 阶梯选中 victim 但操作失败；打印该 state 的 residency/pins/refs 与 Host 占用 |
| `[ladder] pressure demote unstaged …` | 压力规划选定的降级在运行期无法暂存（放置已变），随后会尝试腾容量重试 |
| `[state-store] D2H demote` / `D2H copy` | 状态从显存降级到内存（含槽位号） |
| `[state-store] anchor host evict handle=… host_slot=… pinned=…` | Host 池满：驱逐该锚点的 Host 副本腾槽（§4.4③）；`pinned>0` 时该锚点作废，待 owner 重新发布 |
| `[state-store] allocate FAILED role=… free_object=… free_device=…` + 槽位快照 | 状态池耗尽；随后打印每个占用者的 role/槽位/引用/pin 状态 |
| `[state-store] take_device_slot: NONE FREE` | Device 状态槽位耗尽（随后是快照） |
| `[stale] checkpoint_summary handle=… gen=… frontier=… kind=…` | 释放了不该释放的状态（500 前兆，见 §4.4②） |
| `capture: reserved frontier=… reason=device-fork\|host-snapshot private=… shared=…` | 锚点/共享前缀**发布**成功：落点、是否含私有部分、状态放置方式；`identities+anchor\|+closure\|+shared` 说明该 frontier 会发布哪些 identity（同一 frontier 可带 closure 与长锚点，只有长锚点能被兄弟请求复用） |
| `capture-plan: frontier=… rewrite=… anchor=… shared=… order=…`（`NINFER_REUSE_DIAG=1`） | admission **计划**要捕获的全部 frontier 与 identity；与 `capture:` 对照即可区分"没计划"与"计划了却被跳过" |
| `prefill-step: cursor=… base=… prompt=… next_capture=…/… [frontier…]`（`NINFER_REUSE_DIAG=1`） | 每次 prefill step 的游标、复用 base 与剩余 capture frontier；`(passed)` 标记计划里被越过的 frontier。2026-09-22 定位"每请求只捕获一个锚点"靠的就是这一行 |
| `capture: skip frontier=… reason=…` | 捕获未发布及其**原因**：`cancelled`、`no-publication`、`pressure-invalid`、`static-infeasible`（`add=/used=/cap=` 逐维度数字）、`exact-resident-baseline-infeasible`、`pressure-baseline-infeasible`；此前这些路径完全静默 |
| `capture: shared-planner-skip frontier=… reason=no-positive-net-gain` | 共享发布因 NetGain 非正而跳过；私有 baseline 仍照常发布（§6.2） |
| `capture: degrade frontier=… reason=stale-shared-replacement` | 规划器选定的共享替换目标在预留前已失效：放弃共享发布（可选），保留该请求自己的私有检查点，请求不受影响 |
| `capture: skip frontier=… reason=state-destination-unavailable` | 阶梯也腾不出 device/host 状态目的地：跳过该次捕获（可选），请求继续；满池 + 多路并发发布锚点时出现 |
| `catalog: clear retired private/shared owner slot=…` | 捕获规划的 owner 映射发现 Program 侧已退休的 owner（catalog 视图落后一步）：清除该 entry 并把它排除出规划域，不再抛 `capture owner has no planning ID` |
| `capture: skip frontier=… reason=replacement-not-plannable` | 某个 shared 场景要替换的 owner 已不在规划域内：跳过该场景，私有基线照常发布 |
| `capture: skip frontier=… reason=capacity-reserved-for-newest` | 破坏性回收额度（见下行）已用完：只有最新边界还能退休整会话腾容量，比它更浅的 frontier 一律跳过，避免为投机锚点反复驱逐别人的会话 |
| 计数器 `prefill.destructive_reclaims`（每次捕获预留重置） | 本请求已花掉的**破坏性回收**次数。上限为 1，且只有最新的 2 个捕获 frontier 有资格触发；每次触发记一行 `[ladder] retire site=capture-reclaim ok=1` |
| `materialization: re-plan after capacity miss site=…` | 复用需要的 state/KV 容量连阶梯也腾不出来：重新规划（通常退回 root 冷 prefill），请求继续；`site` 指明是哪个预留点 |
| `materialization: re-admit after progress capacity miss site=…` | 物化在**准入之后**才发现容量不足：回滚该次物化并把请求放回候补队列，下一次准入按 root 重算。`site` 指明是哪个预留点（如 `materialization state reserve_destination after LRU evict`）。此前这条会以 500 结束（`prepared prompt is empty` 或原始异常文本） |
| `capacity re-plans N`（请求日志）/ `materialization_capacity_replans`（引擎统计） | 降级计数：N>0 表示这次请求的复用被池子拒绝、改为重算。**降级是可见的**，不是静默兜底 |
| `[exhaust] drop oldest idle continuation slot=…` | 阶梯最后一档：丢弃最老的空闲会话（并释放它持有的共享前缀引用）。满池时它**必须**能成功；`retire site=… ok=0` 才是"真的没得删" |
| `[engine] request N gave up after M re-plans` | 该请求连续 M 次规划都无法落地：只失败这一个请求并给出原因，引擎继续服务 |
| `[slow] engine-unit=… elapsed=…` | 某个引擎单元超过 100 ms（`progress-context-transaction`、`settle-terminal-requests`、`try-admit-one`、`resolve-prefill-progress`）：把"某个 host 阶段花了 N 秒"细化到具体单元 |
| `[slow] capture-plan owners=… scenarios=… planner=… total=…` | 捕获预留超过 100 ms 时的分段计时：owner/checkpoint 建表、场景数、planner 搜索、总计（2026-09-22 用它定位到 planner 的 target×domain 成本） |
| `[slow] state-destination iterations=… elapsed=…` | device 状态目的地的回收循环超过 100 ms：迭代次数与是否最终取得槽位 |
| `[slow] retire site=… elapsed=…` / `[ladder] retire … elapsed=…ms` | 阶梯退休耗时（实测单次约 2 ms，与 TTFT 秒级停顿无关） |
| `[engine] fatal: …` | Engine worker 捕获到无法恢复的异常：清空全部会话状态并置为 failed（此后 503 直到重启）。行内是该异常的文本 |
| `catalog: clear retired private/shared owner slot=… frontier=…` | Program 已在预留时退休该 owner，但 catalog 仍列出它；candidate 循环发现后清除该 entry（§4.4⑥） |
| `[capture] retained Fork source=… is HostOnly but its reserved destination role=… was not published` | 计划假设在 seal 之后被破坏（源变成 HostOnly 而预留目的地未发布）；带 `reserved_count/state_slots/restore/fork_dest/split/protected` 现场数据 |
| `[FATAL] slot_strict` / `[FATAL] release_*` | 释放路径发现真实不变量违例 → terminate |
| `[serve] EXCEPTION …` | serve 层捕获异常；消息带**抛出点标签**（如 `materialization state restore after LRU evict`） |

### 7.1 观察驱逐与恢复

```bash
grep -c "\[evict\] slot=" ninfer_serve.log        # 会话驱逐次数
grep -c "\[exhaust\]" ninfer_serve.log            # 内存不足丢弃最老的次数
grep -n "HTTP 500\|HTTP 503" ninfer_serve.log     # 可用性事件
grep "done | openai-chat" ninfer_serve.log | tail # 每请求 cache 比例与复用路径
```

判断恢复是否成功应以**服务端返回的 `cached_tokens` 比例**与 TTFT 为准；测试脚本里
"比首次快一半"这类启发式判据在首次基线已被预热时会误报。

## 9. 设计决策：不引入独立的恢复索引

曾经实现过一个"恢复索引"（`StateIndex`/`KVIndex`）：把被驱逐会话的 StateImage 与 KV 地址
空间按前缀指纹登记，回来时再"认领"回 catalog。它已被**整体移除**，依据是三条实测结论：

1. **它不增加容量。** 每条索引条目同样 pin 住一个 Host StateImage 槽位与一段 Host KV，
   与"把会话留在 catalog 里"花的是同一笔内存额度；能记住的会话数由额度决定。
2. **它在最需要的时候用不上。** 认领需要一个空闲 catalog 槽位（并经精确前缀校验），而会话
   被驱逐正是因为 catalog 满了；实测 26 次尝试中有 10 次因此直接返回。
3. **它的 pin 语义正是当日多次 500 的根因。** pin 让 `release()` 永远失败，从而占住 Device
   状态槽位与 KV 地址描述符直至池耗尽；索引驱逐还可能释放活会话仍在使用的状态。

移除后的对照实测（同一套负载）：

| 场景 | 移除前 | 移除后 |
|---|---|---|
| 20 对话 × 2000 词（生产，清缓存重启） | 5/5 HIT | **5/5 HIT**，缓存 99.3%，TTFT 0.26-0.37 s，0 错误 |
| 混合负载（9 种尺寸 + 反复切换 + 大对话回访） | 大对话回访 `cache 0%`、11-16 s 全量重算（FAIL） | **ALL TESTS PASSED**，0 驱逐、0 错误 |
| 压测配置 20+40 对话 | 依赖 pin 容错路径 | 70 请求 / 66 次驱逐 / 0 错误，RSS 稳定 3.77 GB |

也就是说：pin 造成的资源占用本身就在迫使检查点频繁换出——移除后压力显著下降
（`[exhaust]` 在常规与极紧配置下都不再触发），大对话回访也随之恢复正常。

### 11.4 锚点只在消息边界产生（重要）

自动锚点由前端按 `message_boundaries` 放置，且要求 `message_count > 1`
（`src/targets/qwen3_6/impl/frontend/frontend.cpp`）。因此：

- 单条 user 消息的请求**不会**产生任何内部锚点，无论 `--first-anchor-spacing` 多小；
- 要观察锚点与"中段恢复"，测试必须发**多轮对话**。

候选与保留策略（2026-09 修订，修复长对话分叉 0 命中）：

- 自动长锚点候选取**每条 user 消息之前**的那个边界（`message_boundaries[m]`，m 为该 user 消息的
  下标），取最近 N 条（`--auto-long-anchors`，**默认 5**），且两个锚点之间**至少**一个"窗口步长"。
  四条都是必需的：
  - **在 user 消息之前**：客户端是"改写/分叉某条 user 消息"来重入会话的，能复用的前缀是那条消息
    **之前**的全部内容（含紧邻的助手回复）。锚在 user 消息之后则那段助手回复无人覆盖，每次编辑都
    要重算（2026-09-22 实测：7 条消息、prompt≈1,335，编辑最后一条 user 消息命中 947/70.9%，
    锚在消息之前后 1,140/85.4%）。
  - **最近 N 条**：工具循环内部的边界没有请求会停下，若全入候选会灌满预算（实测事故：16 个锚点全挤在
    最近 ~40k 的工具消息密集区，119k 处的分叉 0 命中、重算 119k）。
  - **步长随对话缩放**：步长 = `--first-anchor-spacing`（默认 4096）与 `prompt 长度 / (N+1)` 的较小
    者，下限 **1024** token。固定步长 + 短轮次（真实工作会话的常态：一轮几百 token）会让"最近 N 个
    边界"窗口只剩下最新那一个锚点——每个候选都因间距不足被跳过（2026-09-22 实测：23k 对话里
    14.2k 处的分叉只复用 5.3k / 37%，因为可用的只有最新边界与第一个 spread 锚点）。缩放后同一分叉
    命中 ~94%。下限 1024 表示"一个 host state slot 约等于它省下的 1 秒 prefill"（实测 prefill
    ≈1.1k tok/s）。
  - **被间距挡掉的候选不消耗名额**：只有未解析（折叠的指令消息）的候选消耗 N 个名额之一，因此 N 的
    语义是"N 个锚点铺满会话"，而不是"N 个候选挤在尾部"。间距内的最新边界**始终保留**（它是改写最后
    一条消息的唯一复用点）。
  `--auto-anchor-spacing` 间距骨干保持不变，覆盖长 prompt 与无用户轮的区域。
- **编辑两条锚点之间的那条消息，退回它之前的锚点**：命中点只会落在已发布的检查点上，所以中间那段
  （在交替会话里 = 一条助手回复 + 之后的消息）仍然要重新 prefill。缩放的步长把这个损失限制在"一步"
  之内：2026-09-22 实测同一形状下，4.8k 会话中段分叉 0%→62%、23k 会话中段分叉 37%→63%（此前唯一
  可退的锚点在 5.3k 处）。**续写**不受此限：追加消息时上一轮的 endpoint / `response replay` 检查点
  覆盖整段历史（实测 77.4%）。
- **满池时只有最新边界一定发布**：窗口的深层成员需要腾出别人的检查点才能发布，而每请求的破坏性回收额度
  花在最新边界上，因此它们会以 `capture: skip reason=pressure-no-private-baseline` 被跳过（2026-09-22
  实测 320/320：4.8k 会话中段分叉命中 801/3,883=21%、23k 会话中段分叉 7,157/14,208=50%；同一形状在小池
  有空间发布时为 62%/63%）。这是容量决策（`--host-state-slots`，或允许冷请求花更多次回收），不是前端
  提案的缺陷：最新边界——也就是下一条消息要复用的那个——始终发布。
- 满额保留不再"替换最浅"：改为抽掉使锚点集最接近**等间距**的那个（间距平方偏差最小），
  并钉住最浅头锚；若新锚点冗余（不抽已更均匀）则跳过不发布。锚点集因此大致等距铺满整个
  会话跨度，老消息保留恢复点，尾部由实时端点覆盖。

实测（生产配置，20 条单轮 + 20 条 8 轮对话）：单轮对话的驱逐行一律 `anchors=0`；
多轮对话则出现 `anchors=6` 等取值，且被 20 条新会话挤出后回访仍是 **100% 缓存 / 0.25 s**。

### 11.5 内存利用实测

| 配置 | 负载 | 结果 |
|---|---|---|
| 生产（catalog 16+8，锚点 8192/32768） | 30 条单轮 2000 词 | 驱逐 29 次；峰值 **host_state 42/320（13%）、host KV 0 MiB**；500/503 = 0 |
| 生产（catalog 64+16，锚点 8192/32768） | 60 条 4 轮对话 | 峰值 **host_state 227/320（71%）**、device_state 8/8、host KV 0 MiB；3/3 回访命中 99.5%、17 次驱逐、0 错误 |
| 生产（catalog 64+16，锚点 512/1024） | 150 条 4 轮对话 | 峰值 **host_state 246/320（77%）**、87 次驱逐、anchors 峰值 2、0 错误 |
| 压测（锚点间距 100、单会话锚点 32） | 12 条 6 轮对话 + 10 条施压 | **21 次驱逐**、host_state 8/8 打满、anchors 4、0 错误；回访全 MISS（内存确实不够，符合"丢最老"预期） |

每个被跟踪会话的实际开销（由 246/64 反推）：**约 3.8 个 Host 状态槽 ≈ 560 MiB**（端点 + 约 2 个
锚点 + 工作副本）。据此，catalog 上限与 Host 状态池的关系是：16 → 13%、64 → 71-77%、
80 → 约 94%、96 以上会被 320 槽的池子上限卡住。

结论：catalog 从 16+8 抬到 64+16 后，Host 池在 60/150 会话负载下的峰值从约 13% 升到 71–77%，
已分配的内存因此被真正用起来。限制"能记住多少会话"的仍不是内存额度，而是 catalog 上限
（64；继续抬高到约 80 后池子即逼近上限，需同步缩减每会话锚点数）与会话内的检查点数量
（锚点只在消息边界、且需多轮）。Host KV 基本为 0：短会话的 KV 常驻显存，32 GiB arena
是长会话的保险。想记住更多会话，应抬高 catalog 上限并相应缩减每会话锚点数，
而不是增加新的索引结构（见 §9）。
