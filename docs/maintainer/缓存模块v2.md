# 缓存模块 v2 —— 两级缓存的设计意图

本文只写一件事：**缓存应该按什么规则运转**。它是设计意图，不是实现说明；实现落点、字段名和调用关系在
[资源调度与上下文缓存](resource-scheduling-and-context-cache.md) 与 [分页 KV 上下文存储](paged-kv-cache.md)。

本文件与前者的关系：**规则以本文件为准**。v2 落地后，前者中关于"谁能决定删除、按什么排序、何时停止"
的章节被本文件取代，不再并存两套说法。

---

## 一、设计意图

> 缓存只有两级，规则只有三条。

```text
显存（快、小、贵）
   ↕ 搬
内存（慢、大、便宜）
```

```text
R1  显存满了   → 把显存里最不重要的数据搬到内存        （只搬，不删）
R2  内存满了   → 把内存里最不重要的数据删除            （只删内存侧）
R3  新请求来了 → 显存命中就用；显存没有、内存有就恢复到显存；都没有就计算
```

排队是 R1/R2 都腾不出空间时的等待手段，不是第四条规则：

```text
R0  搬不动（源正在被计算）且 删不出空间（内存已无可删）
    → 请求入队等待；只有队列超时才拒绝
```

**这四条就是全部。** 任何缓存数据的去留，都必须能用它们说清楚；说不清楚的，就是设计外的路径。

## 二、两个名词，必须唯一

### 2.1 "数据"指什么

**保留的单元是"一条对话"**：它在两侧各占 KV 字节和 state 镜像字节，两样加起来是它在该侧的总占用。
下面四种数据是它的**构成**，不是独立的保留对象——所以搬和删都以对话为单位。

缓存路径里只有四种数据：

| | 显存侧 | 内存侧 |
|---|---|---|
| KV | 显存 KV 页 | 内存 KV 页 |
| 状态 | 显存 state 镜像 | 内存 state 镜像 |

**不属于缓存数据的东西**：catalog 槽（索引）、正在被 4 路并发计算的活体数据（它是工作集，不是缓存）。
这两者不参与 R1/R2 的选择。

### 2.2 "最不重要"指什么

**只有一个排序函数 `importance(x)`，全路径共用，没有第二套。**

- 今天代码里并存 7 套各自的排序（分数、retention weight、命中计数、owner 类别、fair-share 保护…），
  同一条数据在不同入口会得到不同名次——这是复杂度和错误的来源，v2 全部废除。
- fair-share 之类的"保护"在 v2 里不是另一套规则，只是 `importance` 的一个取值（受保护 ≈ 不可淘汰）。
- 排序只在两处被使用：**R1 挑搬谁、R2 挑删谁**。其它地方一律不许再各自排一遍。
  （阶梯最后一步的退役也是 R2——它删的就是内存里最不重要的那条对话，所以它不是第三处排序，
  它和缓存策略走同一条链。）

#### 打分契约

```text
score(x)  = victim_value_ns(x) × victim_score_ns(x)
            └ 重建这条对话要花的 prefill 时间 × retention 权重，再加需求窗口里观察到的价值
            └ 再乘"按时间衰减的复用证据"：命中越多越高，越久没被重读越低，有下限
            即  重建成本 × (1 + 命中) × 新近度     —— 只有这一个式子

importance(x) =   未受保护:  clamp(score(x))
                  受保护:    K + clamp(age(x))     // K 高于任何 score；age 越小越旧
```

- **受保护组内部按 `age` 排（最久没动的先让位）**，这就是"阶梯一次放开最老一档"的含义。
- **`K` 不能取 `UINT64_MAX`。** 取最大值会把受保护组内部的次序抹平成同一个常数；而一轮
  填充会把所有对话都划进近时窗口（60 秒内全被摸过），于是整池 `importance` 全部相等，
  排序退化成 `id` —— 实测踩过：日志里每个 victim 都是
  `importance=18446744073709551615`，Host KV 全程 0 MiB（正常应涨到 395 MiB），
  `state_index` / `prefix_switch` 全部丢命中。
- **链只有一条**：`value → age → id`（`id` 只为可复现）。两处消费方——阶梯的
  `retire_preference_order` 与缓存策略的 `cachep::plan`——共用它。
- **分值只算一次**（common 层同时持有 cost model 与观测历史）。调用方只上报**值**，
  不再上报名次：见 §6.2，规划器交出的是 `OwnerImportance{owner, value}`，
  由策略自己排序。

## 三、规则细节

### R1 显存满了 → 搬到内存

- 操作对象：**显存里 `importance` 最低的那条对话**（整条搬，不搬一半）。
- 结果：显存腾出空间，内存多占一份。**显存侧数据量减少，但没有东西被销毁。**
- 活体数据不在候选里（它正在被计算，搬不动）。
- 内存没有空间接收时，先执行 R2 腾地方，再执行 R1。

### R2 内存满了 → 删除

- 操作对象：**内存里 `importance` 最低的那条对话**。
- 删除粒度是**整条对话**：它的内存 KV、内存 state 镜像、目录行**一起释放，不留半个**。
  两个内存池（KV 按字节、state 按槽）各自只负责报告"我满没满"，**谁被删由一个对话级排序决定**。
- **显存侧永远不执行删除。** 显存上的数据只有两种归宿：正在用，或整条搬到内存。

### R3 命中与恢复

- 显存命中 → 直接用。
- 显存未命中、内存命中 → 恢复到显存；这一步可能触发 R1（恢复本身要占显存）。
- 都未命中 → 计算，并按 R1 的规则决定放哪一级。

### R0 排队

- 只有当"要让位的那份数据正在被计算"且"内存也删不出地方"时才排队。
- 排队是在等**正在跑的请求算完腾出工作集**，不是在等缓存被销毁。
- 队列超时（现有 `pending-timeout-ms`）才拒绝。**正常情况下不拒绝。**

## 四、不变量（违反任何一条就是 bug）

1. **删除只可能发生在内存侧。** 显存侧不存在删除操作——编译期或断言期不可达。
2. **显存满且内存有空时，删除数必须为 0。** 只能搬，一个缓存条目都不许销毁。
3. **删除数量 == 缺口数量。** 缺几页删几页，不允许"按批次/按上限"多删。
4. **`importance` 只有一个。** 任何模块自己再排一次序，即视为违规。
5. **缓存数据的去留只由一个模块决定。** 其它模块只能提出需求（"给我 N 页显存"），不能点名受害者。
6. **一条对话永远是完整的。** 搬 = 整条从显存到内存；删 = 整条从内存消失（KV + state + 目录行同时释放）。
   不允许出现"目录里还登记着、state 槽还占着，但 KV 已经没了"的半死对话——它既不能被恢复，
   又白占最稀缺的资源，还会让 R3 的命中变成假命中。

## 五、和现状的差距

### 5.1 今天的结构

同一件事（"腾地方"）被实现了九遍，彼此独立、各自排序、各自决定何时停：

| # | 现有入口 | 位置 |
|---|---|---|
| 1 | 毁灭回退 `root_capped_target` | materialization_planner |
| 2 | 引导闭包强制删一个（`minimum_evictions=1`） | materialization_planner |
| 3 | 物化事务受害者 | `program_impl.h:6278` |
| 4 | capture 事务受害者 | `program_impl.h:9736` |
| 5 | 阶梯 `retire_oldest_idle_continuation` | `program_impl.h:7232` |
| 6 | fair-share 释放 | resource_manager |
| 7 | checkpoint 丢弃 | 独立于会话删除 |
| 8 | 请求失败清理 | `program_impl.h:11814` |
| 9 | 引擎失败清理 | `program_impl.h:10779` |

其中 3/4/5 都调用 `release_continuation_slot_strict`——**一次同时释放显存和内存两侧的"合订本"**。
这正是不变量 1 所禁止的东西。

### 5.2 一条生产记录证明了它错在哪

2026-09-25 21:51，生产实例：

| | 实测 |
|---|---|
| 缺口在哪 | 显存 KV 差 371 页、显存 state 差 1 个槽 |
| 内存状况 | 空 16 个 state 槽 + 12 GiB |
| 实际动作 | 删除 **49 个会话 + 219 个 checkpoint** |
| 释放出来 | **219 个内存槽 / 15 GiB**（显存侧只动了 1 个槽） |
| 结果 | 内存从 87 涨回 118，那 15 GiB 13 分钟没人用 |

用本文件的规则复盘，正确路径是 **R1：把 371 页（约 1.2 GiB）搬进内存，一个会话都不删**。
内存空着 12 GiB，空间绰绰有余。

同一次日志里还有一组关键数字：**144 个"不删"的方案被评估，0 个可行**；而组合阶段显示这些方案
合计能释放 418 / 645 / 1723 页显存。**组合说能腾，评估说不够**——这两组数对不上，是 v2 落地前
必须钉死的唯一事实（见第八节）。

### 5.3 容量本身没有问题

| 池 | 容量 | 合同 |
|---|---|---|
| 显存 state | 8 | 4 路活跃 + 4 个检查点/锚点缓存位 |
| 显存 KV | 10284 页 = 658,176 token | 4 路并发各约 164,544 token |
| 内存 state | 320 | 缓存 |
| 内存 KV | 32 GiB | 缓存 |

**这些是按并发 4 算好的，不是不够。** 显存里同时装着约 6600 页缓存和约 3500 页活体；活跃需求上涨时
让位的是缓存，让位方式是 R1。

host arena 与 extent。

## 八、已钉死：组合与评估没有分歧

> 本节原先是 v2 的开工闸门（"在钉死之前不动代码"）。2026-09-26 已按下面的方式钉死，闸门开启。

**结论：不存在"组合说能腾、评估说不够"。那是日志读法把释放量扣了两遍造成的错觉。
甲成立、乙不成立 —— 正路没有被低估，R1（只搬不删）不需要先修评估，可以直接落地。**

钉死方式（只读日志与源码）：把同一个 target 的 `[compose]` 行与紧随其后的
`[search] target infeasible` 行配对，比较二者的释放量与 `peak`。rig 全量 battery 日志 953 对配对：

- `claim == proj_removed` **953 / 953 全部相等**，没有"说了不做"；
- 同一占用状态下 **`peak + claim` 恒为常数**：`used=808` 时恒为 264、`used=1004` 时恒为 264、
  `used=1024` 时恒为 46/47/48，而其间的 `claim` 各不相同（9、10、133、182…）。
  也就是说 `[search]` 打印的 `peak` **已经减掉了本 target 自己的释放量**，`used` 却是减之前的原始占用。

于是原先那种比法是错的：拿 `claim` 去比 `used + peak - cap`，比的其实是
`claim ≥ 真实缺口 - claim`，等于要求 `2 × claim ≥ 缺口`，把释放量扣了两次。

**正确口径**：`used + raw_peak - claim ≤ cap`，其中 `raw_peak = peak + claim`。

按这个口径复核那 99 对"看起来矛盾"的配对：`used=1004, raw_peak=264, cap=1024 → 真实缺口 244`，
而 `claim` 是 133 / 182，**确实不够**，评估判不可行是正确的，两边自洽。

**日志读法约定**（否则会重新得出错误结论）：`[search] target infeasible` 行里
`used` 是原始占用、`peak` 是已扣本 target 释放量的净值，**两者不可直接相加再拿去和 `claim` 比**；
要先用 `peak + claim` 还原原始 peak。

## 十、实现时发现的文档问题（记录待裁定）

落地过程中发现下面几处，**记录在此，不擅自改判据**；裁定后再改本文件或改实现。

1. **§七 判据 #1 引用的用例不存在。** 表里写 `device-only-tight`，全仓库搜不到这个名字。
   真正实现这条判据的是 `tests/test_pressure_prepare_cases.cpp` 里的
   `fresh-prod-shape`（其 `eviction_budget = 0`，注释明确写着"spill first, delete nothing
   while memory has room"）和 `fresh-dev-roomy`。判据本身没问题，是**用例名写错了**。

2. **§七 判据 #3 与仓库测试规范冲突。** 它要求"断言：缓存路径上不存在调用
   `release_continuation_slot_strict`"——这是对**源码文本**的断言，而 `AGENTS.md` 明确禁止
   source-string-scan 类用例（"Do not add tests for ... source-string scans"）。要么把判据改写成
   行为断言（例如：被释放的对话在显存侧占用恒为 0），要么改测试规范——**两者只能选一个**。
   在裁定前，我按行为断言的方向做：已在 `retire_oldest_idle_continuation` 里加了
   `[invariant1]` 探针，实测**147 次退役里 140 次（95%）带着显存数据被删**
   （103 次 continuation、37 次 shared），即不变量 1 当前是被违反的。

3. **§五.1 那张"九个入口"表是 v2 之前的快照，已经过期。** #1 `root_capped_target`、
   #2 引导闭包本次已删除；表里的 `program_impl.h:NNNN` 行号也已经漂移。
   它现在既不是"现状"也不完全是"待办"，读者会误判进度。

4. **R0 的排队语义只定义在准入阶段，没有覆盖阶梯内部。** §三 R0 写的是"请求入队等待"，
   但 `release_state_capacity_step` 是**物化事务中途**的一次腾地方，那里既不能"入队"
   （请求已经在跑）也还没到"拒绝"。当 R1 搬不动（内存满、又没有只在内存侧的对话可删）
   而 R2 也没有候选时，阶梯该做什么，本文件没有规定。**这一条挡住 §六.3**：在它裁定之前，
   我不去改阶梯的释放语义，以免把"违反不变量1"换成"中途卡死"。

5. **§六.1 #7（checkpoint 丢弃）与第 4 条纠缠在一起。** §2.1 说 checkpoint 只是对话的"构成"、
   不是独立保留对象，§六说"删 = 整条对话"，于是阶梯里那一步**按单个 checkpoint 丢弃**
   （`SlotReleaseKind::Drop`）按字面是被禁止的；可是把它去掉之后，阶梯就只剩"整条退役"
   ——而整条退役在显存侧的合法性正是第 4 条没回答的问题。**需要先裁定：当缺口只需要丢一个
   checkpoint、而不是一整条对话时，阶梯该做什么。**

6. **§六.1 把"失败清理"和"腾地方决策"列成了同一件事。** #8 请求失败清理、#9 引擎失败清理
   是"这条请求挂了，把它自己占的资源还回去"，**没有在挑受害者**，也不是因为某个池满了。
   把它们收进"只回答『给我 N 页显存』的分层控制器"在语义上对不上。**需要明确：清理类入口
   是否算缓存路径**；我按"不算"处理（它们仍然直接调用释放原语），没有动。

7. **§六.4 说"7 套排序合并为 importance 一个"，但没说 capture 规划器怎么并。**
   `SharedCapturePlanner::OwnerPolicy` 只有 `{owner, private_retention_weight,
   explicit_shared_credit}` —— **没有 recency、没有命中计数、没有复用证据**，因此算不出
   §2.2 契约里的 `重建成本 × (1+命中) × 新近度`。而且它的 fair-share 排除在代码注释里被
   写成"structurally unevictable"（结构性不可淘汰 = 一条排除规则），与 §2.2"保护只是一个取值"
   直接冲突。**要裁定：是把观测历史（hits / last_active）接进 capture 规划器再统一打分，
   还是明说 capture 不属于 §2.2 的排序范围。** 在此之前我不动它——否则只是把一条排除规则
   换成另一套没有依据的打分。
