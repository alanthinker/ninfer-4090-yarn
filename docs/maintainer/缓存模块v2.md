# 缓存模块 v2 —— 两级缓存的设计意图

本文只写一件事：**缓存应该按什么规则运转**。它是设计意图，不是实现说明；实现落点、字段名和调用关系在
[资源调度与上下文缓存](resource-scheduling-and-context-cache.md) 与 [分页 KV 上下文存储](paged-kv-cache.md)。

本文件与前者的关系：**规则以本文件为准**。v2 落地后，前者中关于"谁能决定删除、按什么排序、何时停止"
的章节被本文件取代，不再并存两套说法。

---

## 一、设计意图

> 缓存只有两级，规则只有三条。

```text
显存（快、小、贵）
   ↕ 搬
内存（慢、大、便宜）
```

```text
R1  显存满了   → 把显存里最不重要的数据搬到内存        （只搬，不删）
R2  内存满了   → 把内存里最不重要的数据删除            （只删内存侧）
R3  新请求来了 → 显存命中就用；显存没有、内存有就恢复到显存；都没有就计算
```

排队是 R1/R2 都腾不出空间时的等待手段，不是第四条规则：

```text
R0  搬不动（源正在被计算）且 删不出空间（内存已无可删）
    → 请求入队等待；只有队列超时才拒绝
```

**这四条就是全部。** 任何缓存数据的去留，都必须能用它们说清楚；说不清楚的，就是设计外的路径。

## 二、两个名词，必须唯一

### 2.1 "数据"指什么

**保留的单元是"一条对话"**：它在两侧各占 KV 字节和 state 镜像字节，两样加起来是它在该侧的总占用。
下面四种数据是它的**构成**，不是独立的保留对象——**谁被保留、谁让位，永远按对话判**（一条对话只有
一个 `importance`，没有第二个入口）。

**动作的粒度以"回答哪个缺口"为准**（不变量 3 要求删多少=缺多少）：

- **搬**：回答显存 state 槽缺口时可以只搬它的 state 镜像，回答显存 KV 缺口时搬它仍在显存的 KV 页。
  搬动不拆对话——任何时刻它两侧都可恢复。
- **删（只在内存侧）**：state 槽的缺口逐出它最不重要的单个 checkpoint/镜像副本（内存 KV 前缀原样
  保留，下次命中从更浅的锚点重算——注意降级会连带截掉该 owner **超过最深存活锚点的 KV 区间**：该区间仍驻留显存时降级直接被拒绝（不变量 1），只有内存侧区间被截断（其本身就是 R2 合法删除））；KV 字节的缺口按整条对话释放它的内存 KV，**并带走它的内存
  state**（不许留下"state 占着、KV 没了"）。
- **目录行的唯一规则**：两侧数据归零才释放目录行。组件被逐出不等于对话消失——它仍完整可恢复。

缓存路径里只有四种数据：

| | 显存侧 | 内存侧 |
|---|---|---|
| KV | 显存 KV 页 | 内存 KV 页 |
| 状态 | 显存 state 镜像 | 内存 state 镜像 |

**不属于缓存数据、但影响腾让的东西**：正在被 4 路并发计算的活体数据是工作集，不参与 R1/R2。
**正在执行的对话价值视为无限，永远不进候选**：排序只能回答"谁最不重要"，而正在跑的会话
根本无法重算，所以它不是"排最后"，而是**根本不进入这个比较**（实现上从
`retire_preference_order`/策略池里直接排除，而不是给它一个很大的分数——大分数仍可能被
"同分时按 id"之类的次序翻过去）。
catalog 槽（索引）不是缓存数据，却是**准入资源**：没有空行时，新对话必须靠释放一条现有对话
拿到它的行（行随释放一起回收，按目录行缺口走同一 importance 顺序——见 §三 R2 的第四种压力）。
释放行不是另一条规则，它就是下面"整条对话"的删除动作。

### 2.2 "最不重要"指什么

**只有一个排序函数 `importance(x)`，全路径共用，没有第二套。**

- 今天代码里并存 7 套各自的排序（分数、retention weight、命中计数、owner 类别、fair-share 保护…），
  同一条数据在不同入口会得到不同名次——这是复杂度和错误的来源，v2 全部废除。
- fair-share 之类的"保护"在 v2 里不是另一套规则，只是 `importance` 的一个取值（受保护 ≈ 不可淘汰）。
- 排序只在两处被使用：**R1 挑搬谁、R2 挑删谁**。其它地方一律不许再各自排一遍。
  （阶梯最后一步的退役也是 R2——它删的就是内存里最不重要的那条对话，所以它不是第三处排序，
  它和缓存策略走同一条链。）

#### 打分契约

```text
score(x)  = victim_value_ns(x) × victim_score_ns(x)
            └ 重建这条对话要花的 prefill 时间 × retention 权重，再加需求窗口里观察到的价值
            └ 再乘"按时间衰减的复用证据"：命中越多越高，越久没被重读越低，有下限
            即  重建成本 × (1 + 命中) × 新近度     —— 只有这一个式子

importance(x) =   未受保护:  clamp(score(x))
                  受保护:    K + clamp(score(x))   // K 高于任何 score；组内仍走同一条链
```

- **受保护只是"抬到所有未受保护者之前"，组内还是同一条链（`value → age → id`）。**
  组内改成只看 `age`（最久没动的先让位）会把 `value` 抹平：rig `important_session` 里那条
  "每轮都被重读的 20 179-token 会话"与一条"刚发布 2 秒的 1 873-token 会话"在组内同级，
  于是前者先丢锚点、再丢轮闭合，追问 20 189 token 全量重算（2026-09-26 实测；闭合被丢的
  根因见 §十.5）。原先"新发布的会话不能被自己引发的压力淘汰"这条顾虑，现在由 `live(x)`
  承担：刚发布本身就值 8 倍，所以组内按 `value` 排不再伤到新会话——2026-09-27 rig 全量
  battery 复测：`state_index` / `prefix_switch` / `prefix_mixed` 与 `important_session`
  同时全绿。
- **`K` 不能取 `UINT64_MAX`。** 取最大值会把受保护组内部的次序抹平成同一个常数；而一轮
  填充会把所有对话都划进近时窗口（60 秒内全被摸过），于是整池 `importance` 全部相等，
  排序退化成 `id` —— 实测踩过：日志里每个 victim 都是
  `importance=18446744073709551615`，Host KV 全程 0 MiB（正常应涨到 395 MiB），
  `state_index` / `prefix_switch` 全部丢命中。
- **"活"要能压过"深"，而且要衰减得快。** `新近度` 不能只是 `[下限,1]` 里的折扣项：那样
  它只能"减少价值"，永远无法让一条刚发布的会话比一条陈旧但深十倍的会话更值钱。实测踩过
  （rig `prefix_switch`）：一条 700 token、2 秒前刚发布的会话，被判成池子里最便宜的东西，
  为一条闲置的 31K 会话让路，于是切回来时 0% 命中。规则是：
  ```text
  活体倍率 live(x) = 1 + 7 × 2^(−Δt / 30s)      // Δt = 距上次活跃；30 秒半衰期
  score(x)         = 重建成本 × (1 + 命中) × 新近度 × live(x)
  ```
  即 **age=0 时 8 倍、90 秒后回到 1 倍**：刚发布/刚用过的价值相当高，但快速衰减回按重建成本
  计价，避免"一小时前用过"也被当成刚用过。执行中/刚发布的会话因此排在所有空闲会话之前；
  没有时间戳（历史不明）的会话保持保守下限 `1/8` 不变。
- **不要给阶梯再叠一道"价格闸门"。** 2026-09-27 实测过一版实现："一次发布若要毁掉比它更有
  价值的会话的 checkpoint，就跳过这次发布"。它作为**硬否决**叠在排序之上，结果
  `degrade declined: ... price=22..25` 而其余门槛全 0：一条 700 token 的受益方拒掉了池子里
  **所有**比它深的 checkpoint，分量淘汰一步也走不了，压力升级到"整条会话退役"，于是挑中
  最小、刚发布的那条会话（`[evict] slot=6 frontier=669`），`prefix_switch` 0% 命中。
  价值与排序是同一件事：要表达"刚发布的价值高"，就把它写进 `live(x)`（这一条链），
  而不是在链外再加一道闸门。**该实现已删除，不要再加回来。**
- **链只有一条**：`value → age → id`（`id` 只为可复现）。两处消费方——阶梯的
  `retire_preference_order` 与缓存策略的 `cachep::plan`——共用 `victim_value_ns` ×
  `victim_score_ns` 这两个因子；`live(x)` 这一乘子目前只在规划器那侧生效（阶梯那侧只有
  复用证据里的近时项，`age=0` 时 0.5），量级差异记在 §十.8。
- **分值只算一次**（common 层同时持有 cost model 与观测历史）。调用方只上报**值**，
  不再上报名次：见 §6.2，规划器交出的是 `OwnerImportance{owner, value}`，
  由策略自己排序。

## 三、规则细节

### R1 显存满了 → 搬到内存

- 操作对象：**显存里 `importance` 最低的那条对话**；一步搬走**回答该缺口所需的它的显存组件**
  （可以整条，也可以只搬 state 镜像或它仍在显存的 KV 页——搬动不拆对话，两侧始终可恢复）。
- 结果：显存腾出空间，内存多占一份。**显存侧数据量减少，但没有东西被销毁。**
- 活体数据不在候选里（它正在被计算，搬不动）。
- **内存没有空间接收时，先执行 R2 腾地方，再执行 R1。**
- **"内存满了"是字节口径，不是形状口径。** 判定 R2 的唯一问题是"内存还能不能接收这次搬动的字节"：
  只要空闲字节够，搬动就必须成功。内存侧的碎片（空闲区被历史搬动切碎、没有一整段连续空间）
  只影响**拷贝的段数**——把一次搬动切成多段落点即可——**不许**变成"放不下"的结论。
  反之，"一次搬动必须落在一整段连续空间里"这种要求一旦写进可行性判定，就会出现
  "空闲 2.5 GiB 却拒收 2.0 GiB"的死锁：评估说不可行、请求入队等超时，而规则说这本该成功
  （2026-09-26 rig：488 页落点 / 2.58 GiB 空闲被判 one-block 拒收 → `blocked_host` →
  `search produced no incumbent` → R0 超时 503）。

### R2 内存满了 → 删除

- 操作对象：**内存里 `importance` 最低的那条对话**（组件动作的取舍也只用这一个排序，
  checkpoint 副本继承其所属对话的 `importance`，按组件自身的新近度打破平手）。
- 删除粒度按缺口（§2.1）：state 槽缺口 → 最不重要的单个 checkpoint/镜像副本；KV 字节缺口 →
  整条对话的内存 KV（连同它的内存 state 一起）。目录行只在两侧归零时释放。
- 两个内存池（KV 按字节、state 按槽）各自只负责报告"我满没满"，**谁被删由一个对话级排序决定**。
- **目录行压力（第四种）**：没有空行时，按同一 importance 顺序释放一条对话来腾出行——行、内存
  KV/state、以及显存数据（经先搬后释）在**这一步里一起回答**；一条对话一步只动一次，不追加
  第二步。原因码 `catalog-not-closable` 走 R0。
- **显存侧永远不执行删除。** 显存上的数据只有两种归宿：正在用，或搬到内存。

### R3 命中与恢复

- 显存命中 → 直接用。
- 显存未命中、内存命中 → 恢复到显存；这一步可能触发 R1（恢复本身要占显存）。
- 都未命中 → 计算，并按 R1 的规则决定放哪一级。

### R0 排队

- 只有当"要让位的那份数据正在被计算"且"内存也删不出地方"时才排队。
- 排队是在等**正在跑的请求算完腾出工作集**，不是在等缓存被销毁。
- **事务中途的腾地方只有一条出路**：物化/capture 事务中途的阶梯（R1/R2）闭合不了缺口时，
  本步**回滚**（一步都不执行，不删除任何东西），请求回到准入队列等待——**不在事务内阻塞，
  不删除显存数据**。可选 capture 的中途失败 = 跳过本次发布，不阻塞请求。
- **不允许静默兜底，也不允许新增致命路径。** 两条一起成立：
  1. **真出问题要响亮失败**——例如 `continuation_summary` 抛异常说明会话清单已经不一致
     （不变量 6 禁止的"半死对话"），把它 catch 掉当成"未定价"继续跑，等于把响亮的 bug 变成
     悄悄选错受害者，这是不允许的；
  2. **但不要制造新的致命路径**——做法是结构上避免新增调用/新增可能抛异常的步骤（复用已经
     算好的东西），而不是在致命点前面套一层 try/catch。目标是**尽量不进入错误状态**，
     而不是让服务带着坏状态继续接请求。
- **重试与拒绝**：内存里的源还在（R3 命中）时，重试仍按 R3 恢复，**不降级为"从根重算"**；
  池（资源修订号）没变化时不消耗重试次数。**拒绝只有两个出口：队列超时（`pending-timeout-ms`）
  或请求自身取消**——任何"试了 N 次就报错"、或"空闲引擎里暂时阻塞就 fatal"的出口都与本条冲突。

  这条在**控制器**里的落法（2026-09-26）：策略目标必须先问"**被复用的那个候选**"，
  再退到 root 候选。普通搜索在池子满时给不出复用方案，但**根方案能从策略拿到 R1/R2 腾让**
  ——那份腾让同样能放下复用，只是过去只问过 root：于是 `reuse offered 6319 but planned from
  root`（日志原话）成了常态，请求白白重算 7 060 token，而源就在内存里。改动后
  `[cache] controller accepted target candidate=reuse`：`fork_hit`、`state_index`、
  `eviction_fix`、`cache_pressure` 的"每个用例里总有一条会话 0% 命中"整类消失。
  **注意**：这里**不是**"没方案就无限等"——空转等待（引擎空闲、池子不动）只会把
  一次可服务的重算换成队列超时 503，实测如此，所以恢复走的是"腾让 + 复用"，不是排队。
- 队列超时（现有 `pending-timeout-ms`）才拒绝。**正常情况下不拒绝。**

## 四、不变量（违反任何一条就是 bug）

1. **删除只可能发生在内存侧。** 显存侧不存在删除操作——编译期或断言期不可达。
2. **显存满且内存有空时，删除数必须为 0。** 只能搬，一个缓存条目都不许销毁。
3. **删除数量 == 缺口数量。** 缺几页删几页，不允许"按批次/按上限"多删；最后一个动作允许超出缺口
   （一条对话的内存 KV 不能拆一半），但 state 组件本身可拆，不应当超出。
4. **`importance` 只有一个。** 任何模块自己再排一次序，即视为违规。
5. **缓存数据的去留只由一个模块决定。** 其它模块只能提出需求（"给我 N 页显存"），不能点名受害者。
6. **一条对话永远是完整的。** 搬 = 它的显存组件到内存，两侧始终可恢复；**对话从内存消失的唯一
   定义** = 它的内存 KV 与内存 state 同时归零，目录行随之释放（释放内存 KV 必须连同它的内存
   state 一起，不许留下"state 占着、KV 没了"）。单个组件被逐出不构成"半死对话"——它仍可恢复。
   不允许出现"目录里还登记着、state 槽还占着，但 KV 已经没了"的半死对话——它既不能被恢复，
   又白占最稀缺的资源，还会让 R3 的命中变成假命中。

## 五、和现状的差距

### 5.1 九个入口（v2 之前的快照）

> v2 落地后，九个入口已收拢、删除或出范围；**剩余差距**（物化与 capture 事务受害者
> 仍执行整条 teardown）登记在 §十。

### 5.2 一条生产记录证明了它错在哪

2026-09-25 21:51，生产实例：

| | 实测 |
|---|---|
| 缺口在哪 | 显存 KV 差 371 页、显存 state 差 1 个槽 |
| 内存状况 | 空 16 个 state 槽 + 12 GiB |
| 实际动作 | 删除 **49 个会话 + 219 个 checkpoint** |
| 释放出来 | **219 个内存槽 / 15 GiB**（显存侧只动了 1 个槽） |
| 结果 | 内存从 87 涨回 118，那 15 GiB 13 分钟没人用 |

用本文件的规则复盘，正确路径是 **R1：把 371 页（约 1.2 GiB）搬进内存，一个会话都不删**。
内存空着 12 GiB，空间绰绰有余。

同一次日志里还有一组关键数字：**144 个"不删"的方案被评估，0 个可行**；而组合阶段显示这些方案
合计能释放 418 / 645 / 1723 页显存。**组合说能腾，评估说不够**——这两组数对不上，是 v2 落地前
必须钉死的唯一事实（见第八节）。

### 5.3 容量本身没有问题

| 池 | 容量 | 合同 |
|---|---|---|
| 显存 state | 8 | 4 路活跃 + 4 个检查点/锚点缓存位 |
| 显存 KV | 10284 页 = 658,176 token | 4 路并发各约 164,544 token |
| 内存 state | 320 | 缓存 |
| 内存 KV | 32 GiB | 缓存 |

**这些是按并发 4 算好的，不是不够。** 显存里同时装着约 6600 页缓存和约 3500 页活体；活跃需求上涨时
让位的是缓存，让位方式是 R1。

## 六、范围

**不动**（与缓存策略无关，且已稳定）：
`.ninfer` 装载、CUDA Graph、MTP 投机解码、vision、YaRN、量化 KV、算子内核、调度器、
HTTP/OpenAI/Anthropic 协议、tokenizer。

**替换**（缓存路径的决策层）：
1. 上表 9 个删除入口收拢成**一个分层控制器**，只回答"给我 N 页显存 / M 个 state 槽"。
2. 规划器**不再点名受害者**（`preferred_owner_ids` 与按价值挑人整套去掉）。
3. `release_continuation_slot_strict` 从缓存路径摘除（`_best_effort` 只保留在失败清理，见第 5 条）；

## 八、已钉死：组合与评估没有分歧

> 本节原先是 v2 的开工闸门（"在钉死之前不动代码"）。2026-09-26 已按下面的方式钉死，闸门开启。

**结论：不存在"组合说能腾、评估说不够"。那是日志读法把释放量扣了两遍造成的错觉。
甲成立、乙不成立 —— 正路没有被低估，R1（只搬不删）不需要先修评估，可以直接落地。**

钉死方式（只读日志与源码）：把同一个 target 的 `[compose]` 行与紧随其后的
`[search] target infeasible` 行配对，比较二者的释放量与 `peak`。rig 全量 battery 日志 953 对配对：

- `claim == proj_removed` **953 / 953 全部相等**，没有"说了不做"；
- 同一占用状态下 **`peak + claim` 恒为常数**：`used=808` 时恒为 264、`used=1004` 时恒为 264、
  `used=1024` 时恒为 46/47/48，而其间的 `claim` 各不相同（9、10、133、182…）。
  也就是说 `[search]` 打印的 `peak` **已经减掉了本 target 自己的释放量**，`used` 却是减之前的原始占用。

于是原先那种比法是错的：拿 `claim` 去比 `used + peak - cap`，比的其实是
`claim ≥ 真实缺口 - claim`，等于要求 `2 × claim ≥ 缺口`，把释放量扣了两次。

**正确口径**：`used + raw_peak - claim ≤ cap`，其中 `raw_peak = peak + claim`。

按这个口径复核那 99 对"看起来矛盾"的配对：`used=1004, raw_peak=264, cap=1024 → 真实缺口 244`，
而 `claim` 是 133 / 182，**确实不够**，评估判不可行是正确的，两边自洽。

**日志读法约定**（缺一条就会重新得出错误结论）：

1. `[search] target infeasible` 行里 `used` 是原始占用、`peak` 是已扣本 target 释放量的
   净值，**两者不可直接相加再拿去和 `claim` 比**；要先用 `peak + claim` 还原原始 peak。
2. `[spill] short by 429496xxxx` **不是缺口**——那是 `full` 端点（requested =
   `UINT32_MAX`，"能搬多少搬多少"的候选）选择后的剩余，恒等于 `UINT32_MAX − taken`；
   真实缺口行（exact 端点）是诚实的。
3. **同一本账**：给两级策略的求和与组合的交付必须按物理页去重（first-wins）。按对话
   求和会承诺 2634 页、组合只交付 1610 页，评估拒绝、引擎锁死（2026-09-26 实例）。
